# Модули игровых механик

Все пакеты в этой папке загружаются через `MechanicModuleLoader` по манифестам `module.cfg`. Загрузчик регистрирует определения компонентов и карточки возможностей в общих каталогах Object Builder. Четыре группы, ранее подключавшиеся напрямую из каталогов, также переведены на этот механизм.

## Пакеты

| Пакет | Назначение |
|---|---|
| `object_identity` | Идентификаторы, состояние включения, имя, теги, фракции и метаданные |
| `visual_appearance` | Спрайты, визуальные части, цвет, прозрачность, тени, обводка и слои |
| `animation` | Анимационные состояния, переходы и события кадров |
| `movement` | Перемещение, ходьба, бег, прыжок, рывок, плавание и маршруты |
| `physics` | Коллизии, масса, гравитация, толкание, притяжение и свойства поверхностей |
| `interaction` | Взаимодействие, подбор, активация, открытие, закрытие, использование и удержание |
| `characteristics` | Выносливость, мана, энергия, голод, жажда, температура, вес, настроение и репутация |
| `combat` | Блок, парирование, уклонение, прицеливание, заряженные атаки, критические удары, комбо и выбор цели |
| `defense` | Броня, сопротивления, иммунитет, щит, отражение снарядов и регенерация |
| `destruction` | Части, стадии разрушения, обломки, добыча, остатки, ремонт, восстановление и взрыв |

## Состояния

Регистрация пакета означает, что его код и определения доступны общим каталогам. Это **не означает**, что каждая возможность уже автоматически подключена к игровому вводу, физике, визуальному контроллеру или игровому циклу.

- `Implemented` — поведение реализовано в модуле и доступно согласно его контракту.
- `Planned` — карточка и локальная логика могут быть зарегистрированы, но для полноценного игрового поведения ещё требуется интеграция с соответствующей системой.

Не помечай возможность как работающую только потому, что её компонент удалось создать.

## Подключение

При запуске Object Builder загрузчик автоматически сканирует непосредственные подпапки, содержащие `module.cfg`. В игровом runtime регистрация дополнительно выполняется перед созданием объекта через `ObjectFactory`.

Каждый пакет должен содержать `module.cfg`, `module.gd`, runtime-компоненты и собственные тесты. Манифест должен точно перечислять ID, возвращаемые двумя методами entrypoint:

- `build_component_definitions()`
- `build_capability_definitions()`

Все runtime-компоненты наследуются от ObjectComponent. Технический контракт API находится в MECHANIC_MODULE_STANDARD.md.

## Общее хранение предметов

Инвентарь и контейнеры используют ObjectItemStackService из scripts/object_system/object_item_stack_service.gd. Каноническая запись содержит item_id, amount, weight и tags; max_stack допускается опустить для совместимости со старыми данными. Дополнительные поля экземпляра сохраняются и участвуют в проверке совместимости стопок.

Общие runtime-методы хранилища:
- get_item_stacks(options = {})
- get_item_count(item_id)
- get_total_weight()
- add_item_data(item_data, amount_override = -1, options = {})
- remove_item_data(item_id, amount, options = {})

Инвентарь реализует их поверх фиксированных слотов; контейнер — поверх компактного списка и дополняет доступом по actor/faction. Старые методы add_item и remove_item сохранены как совместимые обёртки. Вместимость, весовой лимит персонажа, лимиты контейнера, замки и права доступа не объединяются.

## Проверки

Общий smoke-набор запускает регистрацию всех двадцати пакетов и проверяет наличие ключевых карточек и компонентов. Индивидуальные `tests/smoke.gd` остаются локальными тестами своих пакетов; наличие такого файла само по себе не означает, что он автоматически запускается CI.
