# Дорожная карта Object Builder

Я предлагаю развивать Object Builder как отдельный полноценный инструмент внутри Godot, который со временем сможет стать практически универсальным редактором игровых объектов.

Главный приоритет — удобство создания объектов без необходимости разбираться в сотнях настроек. При этом продвинутый пользователь должен иметь доступ к практически любой характеристике.

Поэтому интерфейс нужно проектировать не как огромную панель параметров, а как систему с категориями, контекстными настройками и постепенно раскрывающейся сложностью.

# I. Принципы проектирования

Перед разработкой определим правила, которым должен соответствовать весь проект.

### 1. Простота по умолчанию, глубина по необходимости

- Новичок должен иметь возможность создать дерево за несколько действий.
- Для создания простого объекта не нужно видеть настройки физики, урона, AI и прочего.
- Дополнительные параметры отображаются только после добавления соответствующего компонента.
- У каждого компонента есть базовые и расширенные настройки.
- Сложные параметры скрыты в раскрывающихся группах.
- Никакие важные возможности не должны быть недоступны только потому, что пользователь выбрал простой режим.

### 2. Категоризация всего интерфейса

Категории должны быть везде:

- В библиотеке объектов.
- В списке компонентов.
- В настройках компонентов.
- В пользовательских свойствах.
- В шаблонах.
- В ресурсах.
- В событиях.
- В инструментах редактирования.

Нужно избегать длинных неструктурированных списков.

### 3. Контекстный интерфейс

Интерфейс должен показывать только то, что относится к текущему выбору.

Например, при выборе спрайта показываются настройки текстуры и отображения. При выборе коллизии — настройки формы и физических слоёв. При выборе компонента Health — только характеристики здоровья.

### 4. Единообразие

Все компоненты должны использовать общую систему интерфейса.

Например, звук всегда настраивается одинаково, независимо от того, к чему он подключён: дереву, двери, оружию или NPC.

Это уменьшит количество элементов управления, которые пользователю придётся изучать.

### 5. Никаких разрушительных обновлений

- Плагин не должен владеть пользовательскими объектами.
- Обновления не должны перезаписывать пользовательские настройки.
- Неизвестные компоненты и свойства нельзя удалять автоматически.
- Все массовые изменения должны поддерживать резервное копирование и откат.

# II. Концепция интерфейса

Это один из первых этапов, а не то, что нужно отложить до окончания разработки механик.

## 1. Главная навигация

Я бы сделал четыре основные вкладки.

OBJECT BUILDER

Диагностика

### Принцип работы панелей

Левая панель:

Дерево узлов и компонентов. Здесь пользователь управляет структурой объекта.

Центральная панель:

Визуальное редактирование. Здесь нужно размещать спрайты, точки крепления, коллизии и другие элементы.

Правая панель:

Инспектор выбранного элемента. Показывает только связанные с ним настройки.

Нижняя панель:

Дополнительные инструменты. По умолчанию свернута. Открывается, когда нужно проверить ошибки или ресурсы.

### Обязательные удобства

- Изменение ширины всех панелей.
- Возможность полностью скрыть боковые панели.
- Масштабирование и перемещение камеры предпросмотра.
- Перетаскивание элементов.
- Контекстные меню по правой кнопке мыши.
- Undo/Redo.
- Горячие клавиши.
- Поиск действий через командную палитру.
- Подсказки при наведении.
- Сохранение расположения панелей.

Мой комментарий: не стоит делать интерфейс с большим количеством постоянных кнопок. Например, добавление компонента лучше реализовать через одну кнопку «Добавить компонент», которая открывает каталог с поиском, категориями и описанием.

# III. Дорожная карта разработки

Теперь последовательность самой разработки.

Фаза 1 — фундамент

## Этап 0. Проектирование UX/UI и технической архитектуры

Цель: до программирования определить, как будет работать система.

Задачи:

- Сформировать окончательную структуру главных разделов.
- Создать схему навигации.
- Спроектировать библиотеку объектов.
- Спроектировать редактор объекта.
- Спроектировать каталог компонентов.
- Определить правила раскрытия расширенных параметров.
- Разработать систему уведомлений и ошибок.
- Определить формат сохранения объектов.
- Определить структуру хранения библиотеки.
- Разделить Runtime и Editor Plugin.
- Спроектировать API компонентов.
- Спроектировать систему уникальных ID и версионирования.

Результат: техническая спецификация и макеты интерфейса.

Моя рекомендация: здесь не нужно создавать все экраны до последней кнопки. Достаточно прототипировать основные сценарии: создание дерева, создание пустого объекта и добавление собственного свойства.

## Этап 1. Ядро Object System

Цель: создать основу, на которой будет работать весь конструктор.

Задачи:

- Создать систему ObjectDefinition.

- Создать Object Runtime.
- Реализовать загрузку и создание объектов.
- Реализовать регистрацию компонентов.
- Реализовать взаимодействие компонентов.
- Добавить обработку отсутствующих компонентов.
- Добавить проверку данных.
- Добавить версионирование.
- Создать механизм резервного копирования.

Результат: объекты создаются и работают через новую архитектуру, даже без интерфейса плагина.

Результат: пользователь может открыть плагин, переключаться по разделам и работать с базовым интерфейсом.

## Этап 3. Библиотека объектов

Цель: полноценное управление пользовательскими объектами.

Задачи:

- Создание библиотеки.
- Создание иерархии категорий.
- Создание собственных категорий.
- Создание подкатегорий.
- Поиск и фильтры.
- Теги.

- Настройка коллизий в 2D-окне.

Результат: пользователь самостоятельно собирает структуру игрового объекта.

## Этап 5. Универсальный инспектор свойств

Цель: пользователь может добавлять произвольные характеристики.

Задачи:

- Создание пользовательских свойств.
- Поддержка чисел, строк, логических значений, цветов, ресурсов и массивов.
- Настройка диапазонов значений.
- Группировка свойств.
- Описания и подсказки.
- Значения по умолчанию.
- Отображение условий.
- Скрытие неактуальных параметров.
- Привязка пользовательских свойств к компонентам.
- Сохранение пользовательских наборов свойств.
- Проверка конфликтов идентификаторов.

Результат: объект может иметь характеристики, которые заранее не были предусмотрены разработчиками конструктора.

Фаза 2 — функциональность

## Этап 6. Каталог компонентов

Создаётся каталог компонентов с единым оформлением.

Предлагаемые категории:

| Категория        | Основные компоненты                   |
| ---------------- | ------------------------------------- |
| Внешний вид      | Sprite, Animation, Visual Effects     |
| Физика           | Collision, Physics, Hitbox            |
| Характеристики   | Health, Defense, Damageable           |
| Бой              | Attack, Projectile, Weapon            |
| Взаимодействие   | Interactable, Pickup, Container       |
| Разрушение       | Destructible, Harvestable, Drop Table |
| Звук             | Audio, Audio Events                   |
| Поведение        | Movement, AI, State Machine           |
| Генерация        | Procedural Generator, Random Variant  |
| Пользовательские | Собственные компоненты и расширения   |

Задачи:

- Каталог компонентов с поиском.
- Категории и подкатегории.
- Иконки и описания.
- Предварительный просмотр возможностей.
- Добавление компонента.
- Удаление компонента.
- Настройка компонента.
- Проверка совместимости.
- Проверка зависимостей.
- Возможность регистрации сторонних компонентов.

Особенно важно: компонент должен иметь описание того, какие другие компоненты ему необходимы.

Например, Destructible может требовать Damageable, но не должен автоматически создавать дополнительные игровые системы, не относящиеся к разрушению.

# IV. Дополнительная система удобства интерфейса

Я бы выделил отдельный этап, который будет сопровождать всю разработку. Это не просто набор красивых элементов, а единая система взаимодействия пользователя с конструктором.

## 1. Режимы отображения настроек

Предлагаю три уровня.

Основные

По умолчанию

Только самые необходимые настройки компонента.

Например: здоровье, тип урона, радиус воздействия.

Расширенные

Дополнительные характеристики для точной настройки.

Например: множители урона, задержки, сопротивления, ограничения.

Экспертные

Редкие технические параметры.

Например: внутренние режимы обработки, специальные флаги, тонкая настройка физики.

Режим отображения должен быть независимым для каждого компонента.

## 2. Система поиска

Сделать единый поиск, который сможет находить:

- Объекты.
- Компоненты.
- Свойства.
- Шаблоны.
- Действия.
- Ресурсы.

Например, пользователь вводит «звук разрушения» и получает соответствующие компоненты, события и настройки.

## 3. Контекстные подсказки

Каждый параметр должен иметь краткое описание.

Не нужно заставлять пользователя искать документацию ради понимания одного поля.

Также предлагаю предусмотреть отдельную справку по выбранному компоненту с примерами использования.

## 4. Автоматическая организация настроек

Когда пользователь добавляет компонент, его свойства автоматически группируются по смыслу.

Например:

```
Audio
├── Общие
│   ├── Громкость
│   ├── Радиус
│   └── Группа звука
│
├── События
│   ├── При появлении
│   ├── При попадании
│   └── При разрушении
│
└── Расширенные
    ├── Разброс высоты тона
    └── Ограничение повторения
```

При этом пользовательские свойства тоже должны позволять создавать собственные группы.

## 5. Система предупреждений

Нужно сделать единое место, где отображаются проблемы объекта.

Например:

Проверка объекта: Oak Tree

2 замечания

Ошибка: отсутствует текстура

Компонент Sprite Renderer не имеет назначенного ресурса.

Предупреждение: нет коллизии

Объект может не блокировать перемещение игрока.

Ошибки должны быть кликабельными: нажатие сразу открывает проблемный компонент или свойство.

# VII. Мои главные рекомендации

Есть пять вещей, которые я бы особенно выделил.

1\. Сначала продумать взаимодействие пользователя с конструктором, затем реализовывать механики.

Иначе интерфейс будет постоянно переделываться под новые компоненты. Это дорого и создаёт технические проблемы.

2\. Отдельно хранить объект и его экземпляр в игровом мире.

Это очень важный момент, который нельзя упустить.

Например, библиотечный дуб имеет 100 здоровья. Пользователь размещает 20 экземпляров на карте, а у одного из них меняет здоровье на 200.

Нужно предусмотреть:

- Базовое определение в библиотеке.
- Индивидуальные переопределения конкретного экземпляра.
- Связь экземпляра с исходным объектом.
- Возможность отвязать экземпляр.
- Выборочное применение обновлений библиотеки к размещённым объектам.

Обновление библиотечного дуба не должно неожиданно перезаписывать все 20 деревьев на карте.

3\. Не превращать каталог компонентов в свалку.

Компоненты должны иметь категории, поиск, фильтры совместимости и понятные описания. Дублирующие компоненты нужно выявлять и объединять, а не бесконечно добавлять новые.

4\. Добавить пользовательские рабочие пространства.

Кому-то нужен большой предпросмотр, кому-то — широкий инспектор. Пользователь должен иметь возможность сохранить собственные расположения панелей и переключаться между ними.

5\. Закладывать расширяемость, но не реализовывать всё заранее.

API, уникальные ID и версии данных нужно спроектировать сразу. А сложную генерацию, наследование и автоматизацию можно постепенно добавлять.

# VIII. Приоритеты ближайшей разработки

Я бы начал с такого конкретного порядка:

## Первый рабочий цикл

1. UX/UI-прототип

   Нарисовать библиотеку, редактор объекта, каталог компонентов и инспектор. Проверить удобство сценариев.
2. Ядро данных

   Создать ObjectDefinition, ComponentDefinition и PropertyDefinition.
3. Плагин Godot

   Реализовать навигацию, панели, сохранение раскладки, базовую систему Undo/Redo.
4. Библиотека

   Научить конструктор создавать, сохранять, искать и открывать объекты.
5. Первый редактор

   Создать объект с нуля, добавить спрайт, коллизию и собственное свойство.
6. Первый полноценный шаблон

   Создать дерево с компонентами здоровья, разрушения, добычи, звуков и частиц. Проверить весь цикл.

Моё итоговое решение: первый контрольный объект должен быть именно деревом из текущей игры. На нём можно проверить практически всю архитектуру: визуальную структуру, коллизии, пользовательские параметры, здоровье, получение урона, разрушение, процедурную генерацию, звуки, частицы и выпадение ресурсов. Когда дерево будет создано исключительно средствами Object Builder и будет работать без специальных исключений в коде мира — это будет хорошим доказательством того, что фундамент выбран правильно.

И ещё: я бы сделал отдельный `ROADMAP.md` и `ARCHITECTURE.md` в репозитории, а в `TASKS.md` переносил только конкретные задачи ближайшего этапа. Так документация не превратится в огромный список вперемешку с текущими исправлениями.
