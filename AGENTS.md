# Инструкции для AI-ассистента

## Быстрый старт
1. Сверь default branch и последний коммит. Основная ветка проекта — `main`.
2. Прочитай `PROJECT_STATE.md`, текущие открытые пункты `TASKS.md` и верхнюю запись `CHANGELOG.md`.
3. Открой только те разделы `OBJECT_BUILDER_ROADMAP.md`, `OBJECT_BUILDER_UI_SPEC.md`, `OBJECT_BUILDER_WORKFLOW.md` и `ARCHITECTURE.md`, которые относятся к задаче.
4. Изучи реальные исходники перед изменениями; не полагайся на старые описания, если код говорит обратное.

## Технологии
- Движок: Godot 4.7.2 Standard.
- Язык игровых скриптов: GDScript.
- Основная сцена: `scenes/world.tscn`.
- Основная ветка: `main`. Не создавай дополнительные ветки для обычных небольших изменений без технической необходимости.
- Пользователь синхронизирует локальный проект через GitHub Desktop и запускает его в настольном Godot.

## Приоритеты и границы
- Главный принцип Object Builder: **«Сложность — внутри. Простота — снаружи».**
- Текущий фокус — интерфейс, рабочее пространство, библиотека, надёжность и инструменты редактирования.
- **Новые механики и runtime-компоненты пока не добавлять.** Не расширять каталог и не поднимать Planned в Implemented без отдельного указания пользователя.
- Не возвращать проект к браузерному запуску, Phaser или npm без прямого запроса.
- Не переписывать несвязанный рабочий код и не менять игровые системы ради задачи редакторского UI.
- Сохранять существующие механики, графику, управление и обратную совместимость данных.
- Часто изменяемые числовые параметры держать в `scripts/game_config.gd`, не дублировать баланс в системах и UI.
- Сторонние ресурсы добавлять только после проверки лицензии и записи автора, URL и лицензии в документацию.
- Не хранить секреты, токены или персональные данные в репозитории.

## Архитектура и повторное использование
- `addons/object_builder/plugin.gd` — координатор EditorPlugin: жизненный цикл, соединение с редактором и маршрутизация действий. Не превращать его в место для новых независимых подсистем.
- Универсальные UI-контролы, формы, очистку динамических списков и правила popup-окон брать из `addons/object_builder/ui/ui_factory.gd`.
- Новый одинаковый UI-паттерн сначала искать в UI factory и существующих экранах. Если решение повторяется в нескольких местах, расширить общий helper, а не копировать блок.
- Выносить самостоятельный экран/контроллер в отдельный файл, когда у него есть собственное состояние, жизненный цикл или достаточно большая логика. Не создавать абстракцию ради одного вызова.
- Общие данные и алгоритмы хранить в `scripts/object_system`; UI не должен дублировать runtime-логику.
- Для новых экранов использовать единые правила полей, карточек, пустых состояний, диалогов и сообщений об ошибках.
- Не создавать новые документационные копии уже существующих спецификаций.

## Эффективный цикл задачи
1. Выбери один небольшой законченный результат, который виден пользователю или закрывает конкретный технический риск.
2. Перед кодом проверь, нет ли уже подходящего сервиса, UI helper, ресурса или шаблона.
3. Зафиксируй критерии приёмки и файлы, которые действительно надо менять.
4. Реализуй вертикальный срез без захвата несвязанных задач.
5. Запусти относящиеся к нему проверки и полный CI при изменении общих основ.
6. Сделай один понятный commit на `main`; не дроби атомарную задачу на серию искусственных коммитов.
7. Обнови только документы, для которых действительно изменился статус или контракт.

## Документы — без повторного переписывания
- `OBJECT_BUILDER_ROADMAP.md` — долгосрочные этапы, зависимости и критерии фаз.
- `TASKS.md` — текущие открытые задачи и отметки выполнения; не копировать туда всю дорожную карту.
- `PROJECT_STATE.md` — короткий снимок текущего состояния и известные ограничения.
- `OBJECT_BUILDER_UI_SPEC.md` — подробный контракт элементов интерфейса.
- `OBJECT_BUILDER_WORKFLOW.md` — пользовательский сценарий, не технический план.
- `ARCHITECTURE.md` — архитектурные границы и потоки данных.
- `CHANGELOG.md` — краткая запись каждого пользовательски значимого изменения.
- `README.md` — обзор и инструкции запуска.

Обновления:
- Всегда добавляй запись в `CHANGELOG.md` для завершённого изменения кода или поведения.
- Обновляй `TASKS.md`, только когда задача добавлена, завершена, отложена или изменила приоритет.
- Обновляй `PROJECT_STATE.md`, когда меняется архитектура, версия, ключевая возможность или известное ограничение.
- Обновляй Roadmap/UI Spec/Architecture только при изменении соответствующего плана или контракта.
- Не переписывай все документы после каждого коммита и не дублируй один и тот же список функций в нескольких местах.

## Проверки и достоверность
- Основная CI-проверка: GitHub Actions `.github/workflows/build.yml`.
- Она должна импортировать проект с включёнными редакторскими плагинами, выполнять Object System smoke, UI factory smoke, существующие регрессионные проверки и запускать основную сцену.
- Новые изменения должны иметь автоматическую проверку там, где это возможно. GUI-компоновку, ввод мышью, размеры окон и UX явно помечай как требующие ручной проверки.
- Не утверждай, что GUI проверен, если запускался только headless.
- Не заявляй о запуске, тестировании или исправлении ошибки, если это фактически не проверено.

## Завершение работы
В ответе кратко укажи: что изменено, коммит, что проверено, что ещё требует ручной проверки и как получить обновление через GitHub Desktop.
