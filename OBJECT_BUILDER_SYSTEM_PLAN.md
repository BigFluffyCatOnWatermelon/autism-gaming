# План системы конструктора игровых объектов для Godot

## 1. Основная архитектура

- Создать отдельный плагин Godot — Object Builder.
- Сделать его универсальной системой создания, настройки, сохранения и управления игровыми объектами.
- Разделить систему на три независимые части:
  - Object Builder — редакторский плагин. Отвечает за интерфейс, создание объектов, редактирование, шаблоны и библиотеку.
  - Object System — игровая система. Отвечает за загрузку объектов, их свойства, взаимодействия, поведение и работу механик во время игры.
  - Object Library — библиотека созданных объектов, шаблонов, конфигураций и ресурсов.
- Плагин не должен быть необходим для работы уже созданных игровых объектов. Его можно отключить, но сохранённые сцены должны продолжать работать.
- Игровые скрипты и классы компонентов должны находиться вне папки плагина. Например, `scripts/object_system/`.
- Плагин должен быть модульным: добавление новой механики не должно требовать переписывания всего конструктора.

Мой комментарий: это самое важное архитектурное решение. Не стоит делать большой скрипт, в котором будут одновременно создание объектов, их физика, здоровье, анимации и взаимодействия. Иначе через несколько десятков типов объектов конструктор станет трудно поддерживать.

В Godot уже есть подходящие механизмы: `EditorPlugin` для расширения редактора, а пользовательские `Resource` и `PackedScene` — для сохранения данных и готовых сцен.&#x20;

## 2. Два способа создания объектов

### 2.1. Создание по шаблону

Пользователь выбирает готовый шаблон, на основе которого создаёт новый объект.

Предлагаемые начальные шаблоны:

- Дерево.
- Камень.
- Растение.
- Куст.
- Предмет.
- Оружие.
- Инструмент.
- Здание.
- Мебель.
- Декорация.
- Контейнер.
- Персонаж.
- NPC.
- Животное.
- Враг.
- Ловушка.
- Интерактивный объект.
- Источник света.
- Снаряд.
- Эффект.
- Пустой игровой объект.

Шаблон должен задавать стартовую структуру, а не ограничивать пользователя.

Например, шаблон дерева может содержать:

- Корневой узел.
- Спрайт дерева.
- Коллизию.
- Систему здоровья.
- Систему получения урона.
- Систему рубки.
- Настройки выпадающих ресурсов.
- Систему падения.
- Генерацию пня.
- Эффекты попадания.
- Звуки.

Пользователь может удалять ненужные компоненты, добавлять новые, менять свойства и визуальную структуру.

### 2.2. Создание без шаблона

Полностью пустой объект, в котором пользователь самостоятельно собирает всё необходимое.

При создании предлагается указать:

- Название.
- Категорию.
- Тип корневого узла.
- Способ сортировки по глубине.
- Иконку библиотеки.
- Теги.
- Описание.

Типы корневых узлов для 2D:

| Тип              | Назначение                          |
| ---------------- | ----------------------------------- |
| Node2D           | Обычный объект                      |
| StaticBody2D     | Неподвижный физический объект       |
| CharacterBody2D  | Управляемый персонаж                |
| RigidBody2D      | Физический объект                   |
| AnimatableBody2D | Двигающийся физический объект       |
| Area2D           | Зона взаимодействия или обнаружения |

После создания пользователь попадает в редактор объекта, где добавляет необходимые элементы.

Мой комментарий: оба способа должны приводить к одному и тому же формату объекта. Не нужно создавать отдельную систему для шаблонных и пустых объектов.

## 3. Система компонентов

Это основа конструктора.

Объект должен собираться из независимых компонентов, каждый из которых отвечает за определённую функцию.

Например, дерево — это визуальная часть + коллизия + здоровье + разрушение + выпадение ресурсов + звуки.

### 3.2. Физические компоненты

- Collision — основная коллизия объекта.
- Hitbox — область получения урона.
- Hurtbox — область нанесения урона.
- Physics — масса, трение, упругость, гравитация.
- Movement — перемещение объекта.
- Pushable — возможность толкать объект.
- Destructible — разрушение и смена состояний.
- Attachment Point — точки крепления других объектов.

Особенно полезен редактор коллизий:

- Добавление нескольких форм.
- Прямоугольник, круг, капсула и полигон.
- Изменение формы мышью в 2D-окне.
- Отдельные настройки для разных частей объекта.
- Настройка Collision Layer и Collision Mask.
- Отображение коллизии поверх спрайта в режиме предпросмотра.

- Преследование цели.

## 4. Универсальная система свойств

Это отдельная крайне важная часть.

Пользователь должен иметь возможность добавлять не только готовые компоненты, но и собственные свойства.

Например, он создаёт дерево и добавляет:

- Возраст.
- Вид дерева.
- Высоту.
- Диаметр ствола.
- Скорость роста.
- Плотность древесины.
- Вероятность появления плодов.
- Сезонность.

В конструкторе должна быть кнопка «Добавить свойство».

Поддерживаемые типы данных:

| Тип         | Пример                                       |
| ----------- | -------------------------------------------- |
| Boolean     | Включено / выключено                         |
| Integer     | Количество ударов                            |
| Float       | Скорость роста                               |
| String      | Название вида                                |
| Enum        | Тип дерева                                   |
| Vector2     | Положение точки атаки                        |
| Vector3     | Дополнительные координаты для будущих систем |
| Color       | Цвет частиц                                  |
| Texture2D   | Текстура                                     |
| AudioStream | Звук                                         |
| PackedScene | Вложенная сцена                              |
| Resource    | Ссылка на другой ресурс                      |
| Array       | Список значений                              |
| Dictionary  | Набор параметров                             |

Для каждого пользовательского свойства должны настраиваться:

- Внутренний уникальный идентификатор.
- Название.
- Описание.
- Тип.
- Значение по умолчанию.
- Минимум и максимум.
- Шаг изменения.
- Варианты выбора для Enum.
- Группа в инспекторе.
- Видимость в зависимости от других параметров.
- Возможность редактирования.
- Возможность сохранения в шаблон.

Очень важно предусмотреть не только хранение значения, но и возможность использования свойства игровыми компонентами.

Например, пользователь создал Float `wood_density`. Позже компонент разрушения сможет использовать это свойство для расчёта скорости рубки.

Мой комментарий: не рекомендую хранить все свойства в одном обычном словаре без описания типов. Это сначала кажется удобным, но потом становится сложно проверять данные, создавать интерфейсы редактирования и обновлять старые объекты. Лучше сделать отдельные описания свойств (Property Definition) и наборы значений (Property Set).

Отдельно нужен редактор дерева узлов объекта.

Например:

```
Oak_Tree
├── Visual
│   ├── Trunk
│   ├── Crown
│   └── Shadow
│
├── Physics
│   └── CollisionShape2D
│
├── Components
│   ├── Health
│   ├── Damageable
│   ├── Harvestable
│   ├── DropTable
│   ├── Destructible
│   ├── Audio
│   └── Particles
│
└── Attachments
    └── FruitPoint
```

Пользователь должен иметь возможность добавлять, удалять, перемещать и переименовывать узлы.

При выборе компонента справа открываются именно его настройки, а не все параметры объекта вперемешку.

### Управление библиотекой

- Создание объектов.
- Удаление.
- Переименование.
- Дублирование.
- Перемещение между категориями.
- Изменение тегов.
- Создание пользовательских категорий.
- Экспорт объекта в отдельную папку.
- Импорт объекта из другой библиотеки.
- Поиск дубликатов.
- Выявление отсутствующих ресурсов.
- Восстановление объекта из резервной копии.

Мой комментарий: библиотека должна быть независимой от конкретной игровой сцены. То есть дерево, которое создаётся сегодня, можно будет использовать в совершенно другой сцене через несколько месяцев, не копируя вручную его скрипты и свойства.

Ещё один важный момент: существующие сцены Cozy Village и автоматически генерируемые ассеты нужно хранить отдельно от пользовательской библиотеки. Конструктор не должен перезаписывать их при обновлении.

## 7. Система шаблонов и наследования

Здесь предлагаю предусмотреть три режима.

Обычное копирование

Создание нового объекта на основе существующего. Все компоненты и настройки копируются. Новый объект становится независимым.

Производный объект

Новый объект наследует базовую конфигурацию, но может иметь собственные параметры.

Пример:

```
Tree_Base
├── Oak_Tree
├── Birch_Tree
├── Pine_Tree
└── Apple_Tree
```

Общее поведение находится в Tree_Base.

Дуб, берёза и сосна используют его, но отличаются текстурами, здоровьем, количеством древесины и другими параметрами.

Вариант объекта (Variant)

Позволяет создавать альтернативные версии без дублирования всей структуры.

Например:

- Обычный дуб.
- Осенний дуб.
- Золотой дуб.
- Повреждённый дуб.
- Старый дуб.

Вариант может переопределять только отдельные свойства.

При этом нужно предусмотреть возможность явно отключить наследуемый компонент или заменить его собственной реализацией.

Моя рекомендация: на первом этапе создавать независимые копии. Наследование и варианты добавить после появления стабильного компонентного ядра. Иначе можно потратить много времени на разрешение конфликтов между наследуемыми свойствами ещё до появления самого конструктора.

## 8. Интеграция с игровым миром

Создать отдельный сервис Object Library Runtime.

Его задачи:

- Поиск объекта в библиотеке по ID.
- Загрузка сцены.
- Создание экземпляра объекта.
- Применение параметров.
- Обработка компонентов.
- Регистрация объекта в игровых системах.
- Удаление.
- Сохранение состояния.
- Работа с выпадающими предметами.

В контексте текущей игры особенно важно:

- Объект автоматически регистрируется в системе разрушения, если имеет соответствующие компоненты.
- Наличие компонента Health не должно автоматически означать отображение полосы здоровья.
- Дерево может иметь Harvestable, но не иметь Attack.
- Камень может иметь Damageable, но не иметь Harvestable.
- Сундук может иметь Interactable и Container, но не иметь Health.
- Предмет может иметь Pickup, Inventory и другие свойства.
- Враг может использовать Health, Damageable, Movement, Attack и AI.

Игровой мир не должен проверять конкретные имена вроде `oak_summer` или `rock_large`. Он должен ориентироваться на возможности объекта и его компоненты.

Например, вместо:

```
if object.resource_type == "tree":
    ...
```

использовать проверку возможностей:

```
if object.has_component("harvestable"):
    object.harvest()
```

Здесь пример обозначает желаемый API, а не требование реализовать именно такой вызов.

Это позволит добавлять сотни новых объектов без постоянного изменения `world_controller.gd`.

## 9. Обновления и совместимость

Один из важнейших разделов

Конструктор должен быть рассчитан на многолетнее развитие.

Предлагаю разделить версии на три независимых уровня:

- Версия самого плагина.
- Версия формата данных библиотеки.
- Версия API игровых компонентов.

Например, обновился плагин, добавилась новая возможность компонента Destructible.

Что должно произойти:

1. Плагин обнаруживает старые объекты.
2. Определяет версию их данных.
3. Проверяет необходимость обновления.
4. Показывает пользователю список изменений.
5. Создаёт резервные копии изменяемых файлов.
6. Выполняет преобразование данных.
7. Проверяет корректность обновлённых объектов.
8. Выводит отчёт.

### Обязательные механизмы

- Уникальные ID компонентов и свойств.
- Версионирование объектов.
- Механизм миграции старых данных.
- Резервное копирование перед обновлением.
- Проверка отсутствующих компонентов.
- Проверка удалённых ресурсов.
- Совместимость со старыми сценами.
- Возможность отката миграции из резервной копии.
- Запрет автоматического удаления неизвестных пользовательских свойств.
- Сохранение пользовательских настроек при обновлении.

Особенно важно, чтобы переименование свойства не приводило к потере сохранённых значений. Для этого идентификатор свойства должен быть независим от его отображаемого названия.

Мой комментарий: не нужно автоматически перестраивать все объекты библиотеки после каждого обновления плагина. Сначала следует выполнить проверку и только затем предложить миграцию. Особенно это касается объектов, которые пользователь вручную дорабатывал.

## 10. Предпросмотр и проверка объектов

В конструкторе необходимо сделать отдельную тестовую среду.

Пользователь должен иметь возможность проверять объект, не помещая его в основную игровую сцену.

### Режим предпросмотра

- Просмотр статичного объекта.
- Проигрывание анимации.
- Воспроизведение звуков.
- Запуск частиц.
- Проверка коллизий.
- Проверка взаимодействия.
- Тестирование разрушения.
- Проверка выпадения ресурсов.
- Просмотр разных состояний.
- Отображение точек крепления.

### Автоматическая проверка

При сохранении конструктор проверяет:

- Есть ли корневой узел.
- Назначена ли текстура визуальному компоненту.
- Не потерялись ли ссылки на ресурсы.
- Есть ли коллизия у физического объекта, если она требуется.
- Не используются ли несуществующие компоненты.
- Нет ли повторяющихся ID.
- Правильно ли настроены зависимости.
- Не ссылается ли объект сам на себя через бесконечную цепочку шаблонов.
- Совместимы ли версии данных.

Ошибки разделить на два класса:

- Красные — объект нельзя сохранить или использовать до исправления.
- Жёлтые — объект работает, но имеет потенциальные проблемы.

Также предусмотреть журнал проверок и возможность повторной проверки всей библиотеки.

### 11.2. Система состояний

Объект может иметь несколько состояний:

```
Tree
├── Normal
├── Damaged
├── Falling
├── Stump
└── Removed
```

Каждое состояние может менять:

- Текстуру.
- Анимацию.
- Коллизию.
- Свойства.
- Доступные действия.
- Звуки.
- Частицы.

В дальнейшем это позволит создавать двери, сундуки, разрушаемые стены, растения и другие объекты без отдельных уникальных систем для каждого.

### 11.3. Система событий

Добавить визуальный редактор событий:

```
При получении урона
    ↓
Проиграть звук
    ↓
Создать частицы
    ↓
Изменить состояние
```

Или:

```
При взаимодействии
    ↓
Проверить наличие ключа
    ↓
Открыть дверь
    ↓
Проиграть анимацию
```

События должны иметь условия, действия и возможность связывать компоненты между собой.

### 11.4. Генерация объектов из других объектов

Возможность собирать сложные объекты из отдельных элементов:

- Дом из стен, пола, крыши, дверей и окон.
- Дерево из ствола, веток, листвы и плодов.
- Оружие из основы, рукоятки, лезвия и дополнительных эффектов.
- Мебель из нескольких отдельных деталей.

При этом можно выбирать между объединением элементов в одну сцену и сохранением независимых дочерних объектов.

### 11.5. Процедурная генерация

Дополнительные параметры для объектов, которые должны создавать часть своей структуры самостоятельно:

- Случайная форма.
- Случайный размер.
- Количество ветвей.
- Количество деталей.
- Случайные текстуры из набора.
- Процедурные пни.
- Процедурные эффекты.
- Случайные вариации внешнего вида.

Например, пользователь создаёт куст, указывает диапазон количества ветвей от 5 до 12, а генератор формирует внешний вид.

### 11.6. Связи между объектами

- Родительские и дочерние объекты.
- Прикрепление к костям и точкам.
- Ссылки на другие объекты библиотеки.
- Зависимости от других объектов.
- Объекты, которые создаются при разрушении.
- Объекты, которые появляются при взаимодействии.

### 11.7. Инструменты массового редактирования

Очень пригодится, когда библиотека станет большой:

- Изменить звук у нескольких объектов.
- Изменить материал у группы объектов.
- Изменить настройки коллизии.
- Массово заменить текстуры.
- Найти объекты, использующие старую версию компонента.
- Найти объекты без иконок.
- Обновить параметры по выбранному шаблону.

# 13. Мои дополнительные рекомендации

Есть несколько решений, которые я считаю принципиальными.

1\. Не ограничивать систему существующими категориями.

Категории должны создаваться пользователем. Нельзя зашивать список вроде «деревья, камни, оружие» внутрь кода. Сегодня это дерево, завтра производственный станок, а послезавтра совершенно новый тип интерактивного объекта.

2\. Не привязывать компоненты к конкретным типам объектов.

Например, компонент Health должен работать и у врага, и у дерева, и у сундука. Разница должна задаваться настройками, а не отдельными версиями скрипта.

3\. Добавить возможность собственного кода.

Готовые компоненты покроют большинство случаев, но рано или поздно понадобится уникальное поведение. Нужно предусмотреть возможность прикрепить пользовательский GDScript к объекту или написать собственный компонент через понятный API.

4\. Добавить поддержку сторонних расширений.

В будущем другой плагин должен иметь возможность зарегистрировать собственный компонент, например Fishing, Farming или Magic. Object Builder автоматически обнаруживает его и показывает в списке доступных компонентов.

5\. Предусмотреть импорт и экспорт библиотеки.

В идеале целый объект должен переноситься между проектами вместе с необходимыми зависимостями. При импорте система должна находить отсутствующие ресурсы и предлагать их подключить.

6\. Использовать Undo/Redo.

Любая операция конструктора должна поддерживать отмену: удаление компонентов, изменение дерева узлов, перестановка, изменение свойств. Не стоит заставлять пользователя вручную восстанавливать случайно удалённые части объекта.

7\. Сделать безопасное редактирование.

Перед массовым изменением библиотеки или миграцией данных создавать резервную копию. Предусмотреть предупреждения перед удалением ресурсов, которые используются другими объектами.

8\. Отдельно предусмотреть производительность.

Не нужно постоянно загружать все текстуры и создавать все сцены библиотеки одновременно. Для списка объектов использовать небольшие изображения предпросмотра, а полные сцены загружать только по запросу.

9\. Подготовить поддержку будущих типов проектов.

Начать с 2D, поскольку текущая игра 2D. Но систему компонентов стоит проектировать так, чтобы впоследствии можно было добавить 3D-объекты и UI-объекты через дополнительные модули. Не нужно сейчас создавать универсальную поддержку всего Godot — это сильно усложнит первую версию.

## Итоговая концепция

## Object Builder

Схема взаимодействия основных частей

Редакторский плагин

Создание · Редактирование · Шаблоны · Библиотека

Object Definition

ID, категории, свойства, версии

Object Scene

Узлы, спрайты, коллизии, компоненты

Object Library

Постоянная библиотека объектов и шаблонов

Object Runtime

Загрузка, создание экземпляров, механики и взаимодействия

Игровой мир

Деревья · Камни · Враги · Постройки · Любые новые объекты

Главное решение: я бы строил не просто редактор деревьев, камней и оружия, а полноценную компонентную платформу для создания игровых объектов. Тогда дерево, сундук, враг и производственный станок будут использовать одни и те же базовые механизмы, но с разными наборами компонентов.

И я бы начал именно с фундамента, библиотеки и создания пустых объектов. Не с красивого интерфейса и не с сотни готовых механик. Если правильно спроектировать ядро, все последующие возможности будут добавляться как расширения, а не как очередная переделка конструктора.
