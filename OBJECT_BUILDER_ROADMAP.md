# Object Builder — подробная дорожная карта разработки

**Главный принцип: «Сложность — внутри. Простота — снаружи».**

Цель — один универсальный конструктор игровых объектов внутри Godot. Пользователь начинает с внешнего вида, выбирает понятные возможности, настраивает только нужные параметры, проверяет результат и сохраняет объект. Внутренняя сборка узлов, компонентов, зависимостей и связей остаётся задачей плагина.

**Документ задаёт актуальный порядок разработки.** Он основан на:
- `OBJECT_BUILDER_DESIGN_SPEC.md` — продуктовые принципы и целевая архитектура;
- `OBJECT_BUILDER_UI_SPEC.md` — подробный контракт экранов и элементов интерфейса;
- `OBJECT_BUILDER_WORKFLOW.md` — сценарии пользователя;
- `ARCHITECTURE.md` — внутренние слои, данные и runtime;
- `TASKS.md` — оперативный чек-лист репозитория.

Исходные `ROADMAP.md` и `OBJECT_BUILDER_SYSTEM_PLAN.md` остаются сохранёнными авторскими документами. Этот файл — актуальная рабочая дорожная карта, согласованная с новой концепцией простоты.

## 1. Текущее состояние и правила чтения

### Текущая версия: 0.8.0-dev

**Статус: Object Builder 0.8.0-dev работает в центральном рабочем пространстве. Библиотека объектов, Canvas, визуальный Preview и единый мастер создания с неразрушающим копированием/импортом сцен реализованы на уровне кода и smoke-тестов. Свежий CI и ручная проверка в Godot GUI после последних изменений ожидают подтверждения.**

В 0.5.0–0.8.0-dev реализованы:
- Component Bindings к произвольным узлам, совместимость старых root-level данных и поиск компонентов по дереву объекта.
- 12 профилей создания и вариант «Без профиля».
- Единый реестр встроенных и пользовательских компонентов с проверкой поддерживаемых типов узлов и зависимостей.
- 42 работающие возможности: 40 механик предыдущих версий, подбор предмета и взаимодействие клавишей E.
- Планирование включения/отключения возможностей с проверкой зависимостей, конфликтов, управлением автоматическими зависимостями и Undo/Redo.
- Каталог 200 механик: 20 категорий, ровно 10 записей в каждой. Каждая запись имеет постоянный ID, название, описание и ключевые слова.
- Карточки показывают статус. 42 существующие реализованные возможности доступны; остальные записи остаются недоступными, пока их собственная реализация не готова.
- Capability Definition теперь различает назначение, область действия, способ реализации и готовность; legacy runtime_status сохранён для обратной совместимости.
- Модель поддерживает editor-only и data-only возможности, которым не требуется runtime-компонент. Текущие 200 записей ещё не получили полностью вручную проверенные значения всех новых метаданных.
- Валидация запрещает добавить запись, если её readiness_status не равен ready, независимо от того, создаёт она игровой компонент или нет.

Автоматическая проверка версии 0.8.0-dev: [GitHub Actions run 42226533709](https://github.com/BigFluffyCatOnWatermelon/autism-gaming/actions/runs/42226533709) — импорт ресурсов, разбор скриптов, Object System smoke-тесты, десять пакетных тестов и запуск основной сцены завершились успешно.

**Ручная GUI-проверка остаётся нужна:** headless CI не оценивает удобство списка из 200 карточек, поиск/фильтрацию и расположение окон на разных разрешениях.

### Что пока не реализовано в 0.8.0-dev

Не считать готовыми:
- runtime-поведение 158 механик со статусом «В разработке»;
- полноценную контекстную панель настроек возможностей и нижнюю диагностическую панель с тестовыми результатами;

- обновление/удаление изменённой декларативной структуры уже открытой сцены и связанная с этим Undo/Redo; создание узлов и подключение сигналов при создании объекта уже поддерживаются;
- запуск пользовательской игровой логики в Preview, тестовые действия, паузу и журнал результатов;
- редактор коллизий, хитбоксов, sockets, состояний и событий;
- Instance Overrides, выборочное обновление экземпляров и загрузчик пакетов расширений.

Object Builder уже открывается в центральной вкладке Godot через Main Screen Plugin. Карточная библиотека с компактным списком, поиск/фильтры, сведения о записи, операции над объектами и пользовательские коллекции реализованы на уровне кода и smoke-сценариев. Canvas поддерживает выбор, перемещение, масштабирование и вращение частей; Preview показывает актуальную копию черновика без сохранения временной сцены. Единый мастер создаёт объекты с нуля, по шаблону, копирует сохранённые объекты и импортирует сцены Godot в отдельные черновики без изменения исходника; неизвестные узлы/скрипты/ресурсы сохраняются. Подтверждение этих сценариев в настольном Godot GUI и свежий CI после последних изменений остаются обязательными. Добавление изображения создаёт Sprite2D; расширенная работа с коллизиями и игровыми сценариями остаётся отдельной фазой.

### Как отмечать прогресс

- **Готово** — функциональность реализована, smoke-проверки пройдены, данные сериализуются и старый формат не сломан.
- **В работе** — часть механизма уже есть, но пользовательский сценарий или критерии приёмки ещё не закрыты.
- **Не начато** — задача остаётся планом.
- **Ручная проверка** — отдельно требуется открыть Godot 4.7.2 GUI и проверить удобство, компоновку, мышь, Undo/Redo и сохранение. Headless CI этого не подтверждает.

Версии и фазы ниже — ориентиры выпуска, а не календарные обещания. Фазы можно объединять, если это уменьшает переделки, но нельзя перескакивать через обязательные зависимости данных.

## 2. Неизменяемые правила проекта

Эти правила применяются ко всем фазам и всем типам объектов.

1. **Один конструктор для всего.** Дерево, камень, сундук, предмет, оружие, снаряд, NPC, животное, механизм и здание используют один набор инструментов. Ни один примерный объект не становится основой архитектуры.
2. **Профиль не ограничивает возможности.** Категория или стартовый профиль лишь предлагает начальные значения и подсказки. После создания объект может получить любую совместимую возможность.
3. **Простой режим скрывает реализацию, а не возможности.** В нём не показываются NodePath, ID, технические классы узлов и сырые словари.
4. **Одна модель данных.** Простой и расширенный режимы изменяют один `ObjectDefinition`, одну сцену и один набор свойств. Не создавать две параллельные модели.
5. **Godot остаётся настоящим источником сцены.** Результат — обычная PackedScene с реальными Node, Resource, CollisionShape, SpriteFrames и GDScript. Отключение Object Builder не должно ломать runtime.
6. **Автоматические изменения обратимы.** Установка, изменение и удаление возможностей должны иметь Undo/Redo и понятный план действий.
7. **Зависимости явные.** Плагин может подготовить нужные системы автоматически, но до разрушительных или неоднозначных изменений обязан объяснить последствия.
8. **Не терять неизвестные данные.** Незнакомые узлы, скрипты, ресурсы и расширения сохраняются при редактировании; неподдерживаемые простым режимом части остаются доступны в расширенном.
9. **Без специальных редакторов под конкретный объект.** Разные объекты отличаются данными, выбранными возможностями и составом сцены, а не отдельными ветками UI и runtime.
10. **Простая проверка не требует тестовой сцены.** Runtime проверяется headless smoke-тестами на временно создаваемых узлах. Отдельные демонстрационные `.tscn` не создаются только ради проверки API или вычислений.

## 4. Сквозные правила реализации

Каждую фазу вести через единый цикл:

1. Сначала сверить задачу с UI Specification, Workflow и Architecture.
2. Описать изменение модели данных и совместимость со старыми версиями.
3. Реализовать runtime до или одновременно с UI, чтобы интерфейс не имитировал несуществующую механику.
4. Поддержать Undo/Redo для редакторских операций.
5. Добавить headless smoke-проверки на реальных временных Node/Resource, без отдельной демонстрационной сцены.
6. Проверить сериализацию и повторную загрузку.
7. Запустить Godot CI и дождаться успешного результата.
8. Обновить CHANGELOG, ARCHITECTURE, PROJECT_STATE, TASKS и README.
9. Отдельно указать, что ещё требует ручной GUI-проверки.
10. Только после критериев готовности отмечать задачи завершёнными.

### Запреты на регрессии
- Не возвращать отдельную тестовую `.tscn` ради простой проверки логики.
- Не привязывать новые системы исключительно к деревьям, сундукам, NPC или другому отдельному примеру.
- Не дублировать настройки между Object Builder и штатным Inspector.
- Не делать профиль обязательным.
- Не создавать вторую модель объекта для простого режима.
- Не удалять неизвестные/пользовательские части сцены ради того, чтобы упростить внутренний каталог.
- Не считать успешный headless CI доказательством удобства графического интерфейса.

## Дополнение к фазе 5 — Умный каталог возможностей

Фаза 5 должна начинаться с пользовательского сценария каталога, а не с механического увеличения числа записей. Каталог является контекстной системой поиска, рекомендаций, связей и пакетного добавления.

Порядок реализации:
1. Метаданные и типизация: постоянный ID, тип назначения, область действия (editor-only/runtime/hybrid/data-only), способ реализации, статус, иконки/иллюстрации, синонимы, примеры и схема настроек.
2. Визуальная библиотека: крупные карточки, фильтры, категории, избранное, недавние, установленные и наборы.
3. Типизированные отношения: обязательные зависимости, рекомендации, расширения, альтернативы, реальные конфликты и тематические связи; объяснения каждой связи.
4. Локальный поиск и рекомендации: запросы обычным языком, контекст объекта, объяснимое ранжирование, отсутствие обязательного внешнего AI.
5. Множественный выбор: выбор нескольких записей с сохранением состояния при поиске и фильтрации.
6. Планирование и применение пакета: транзитивные зависимости, дедупликация, проверка конфликтов, предпросмотр плана, атомарное применение и одно Undo/Redo.
7. Наборы/пресеты: редактируемые сочетания, которые не создают отдельные виды механик.
8. Интеграция в главное окно конструктора, контекстные настройки, диагностика и Preview.

**Критерий первого полноценного выпуска:** пользователь находит несколько возможностей, понимает их отношения, выбирает их в одной сессии и добавляет одним действием. Набор либо применяется целиком, либо не изменяет объект.

**Критерий универсальности:** в каталоге на равных правах представлены визуальные, анимационные, звуковые, физические, data-only и поведенческие возможности. Для каждой проверяется реализация в соответствующей области действия; отсутствие runtime-компонента само по себе не является признаком незавершённости.

## Реализация главного конструктора — 2026-11-07

3. Создать полноценные иллюстрированные карточки, реестр графики по постоянным ID и подробности механики.
4. Заполнить реальные рекомендательные/расширяющие/альтернативные связи и построить локальную интерактивную карту.
5. Добавить контекстные рекомендации и более удобную семантическую выдачу поиска.
6. Создать редактируемые наборы механик и интегрировать их в тот же пакетный план.

Эти изменения не означают, что Умный каталог уже реализован; они фиксируют фактический прогресс главного конструктора.


### Новый фундамент конструктора и каталога — 2026-11-07

- Главный редактор разделён на «Внешний вид», «Возможности», «Настройки» и «Расширенный режим».
- В модель Capability Definition внесены kind_id, execution_scope, implementation_type, readiness_status, графические ссылки, синонимы, примеры, отношения и compatibility rules.
- Добавлена совместимость с существующими ресурсами через legacy runtime_status и единый is_ready().
- Smoke-тесты метаданных, списка, выбора, контроллера и batch planner подключены к GitHub Actions; ожидается результат текущего CI.
- Множественный выбор и пакетное добавление уже подключены к существующему Undo/Redo. Следующий приоритет — контекстные настройки и командная панель, затем иллюстрированный каталог и связи.
