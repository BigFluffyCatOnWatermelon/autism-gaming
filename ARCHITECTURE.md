# Архитектура Object Builder

**Продуктовый принцип: «Сложность — внутри. Простота — снаружи».**

Этот документ описывает внутреннюю архитектуру и фактическое состояние системы. Пользовательский интерфейс должен скрывать технические детали за простыми действиями. Внутренняя реализация при этом остаётся универсальной и расширяемой.

Статус: архитектурный документ Godot 4.7.2. Описание целевого поведения не означает, что весь интерфейс или все системы уже реализованы.

Экранная структура, иерархия панелей, полный реестр кнопок/элементов управления и UI-состояния зафиксированы в OBJECT_BUILDER_UI_SPEC.md. Архитектура описывает внутреннюю реализацию, UI Specification — поведение интерфейса, а OBJECT_BUILDER_ROADMAP.md — актуальный порядок разработки и критерии готовности.

## 1. UX-контракт

Простой режим — интерфейс по умолчанию. Пользователь работает с понятиями «Внешний вид», «Возможности» и «Настройки». Он выбирает, что объект должен делать; плагин собирает необходимые узлы, компоненты, свойства и связи.

В простом режиме не показываем пользователю:
- классы узлов Godot и структуру SceneTree;
- внутренние типы/привязки компонентов;
- NodePath и служебные ID;
- сырые словари и технические зависимости;
- обязательное ручное подключение сигналов или скриптов.

Расширенный режим по запросу открывает SceneTree, Inspector, компоненты, свойства, логику и GDScript. Оба режима редактируют одну и ту же модель объекта.

Основная UX-модель:
1. Внешний вид.
2. Возможности.
3. Настройки.
4. Preview.
5. Сохранение и размещение.

Нельзя добавлять отдельные архитектурные ветки для дерева, сундука, меча, NPC или другого названия объекта.

## 2. Слои системы

### 2.1. Object Builder Editor

Путь: addons/object_builder/

Задачи:
- библиотека и мастер создания;
- простой визуальный конструктор;
- каталог пользовательских возможностей;
- контекстные параметры;
- расширенный редактор Godot-структуры;
- Preview;
- понятные ошибки и диагностика;
- импорт, экспорт, обновление и миграции.

Редактор не содержит игровую логику. Отключение плагина не ломает ранее созданные сцены и runtime API.


### 2.1. Editor UI Components

Внутри `addons/object_builder/ui/` находятся переиспользуемые элементы редакторского интерфейса:

- `ui_factory.gd` — общие примитивы контролов и единые правила размеров/диалогов.
- `library_view.gd` — самостоятельная панель библиотеки: поиск, фильтры, список результатов и сигналы пользовательских действий. Фильтрация определений и локальные списки избранного/недавнего остаются ответственностью контроллера.
- `object_editor_view.gd` — оболочка четырёх независимых рабочих областей: «Внешний вид», «Возможности», «Настройки» и «Расширенный режим», каждая со своей прокруткой. Контроллер заполняет предоставленные content roots и связывает их с моделью документа.
- `property_list_view.gd` — отображение пользовательских свойств по группам и сигналы изменения/редактирования/удаления; изменение данных остаётся в контроллере.
- `component_editor_view.gd` — UI выбора категории, доступных компонентов и список подключённых компонентов; каталог, изменение определений и Inspector остаются ответственностью контроллера.
- `capability_list_view.gd` — поиск, категории, карточки с пиктограммами, кнопка просмотра связей, флажки множественного выбора и закреплённая панель добавления пакета; вид не меняет ObjectDefinition напрямую.
- `capability_settings_panel.gd` — встроенная форма параметров установленной возможности в правом Inspector; поддерживает Basic / Advanced / Expert, типизированные числовые/Boolean/String контролы и сигналы Apply/Close. Не меняет модель до подтверждения.
- `controllers/capability_catalog_controller.gd` — независимая сессия множественного выбора, фильтрация, локальный поиск, построение карточных данных, подсветка исходящих/входящих отношений, пакетный план и объяснимая сводка.
- `controllers/capability_selection_session.gd` — хранит только выбранные ID; состояние не зависит от активного поиска/категории/страницы.
- `services/capability_batch_planner.gd` — строит единый план пакета на копиях записей, разрешает зависимости и передаёт итог в существующий ObjectCapabilityService; не изменяет рабочий объект.
- `services/capability_icon_registry.gd` — разрешает индивидуальный icon_resource_path либо стабильную AtlasTexture из общего SVG-атласа по icon_atlas_index; кэширует значки по постоянному ID.
- Настройки из `capability_settings_panel.gd` принимает `plugin.gd`: значения валидируются через `ObjectCapabilityService.build_application_plan()` и применяются одной EditorUndoRedo-командой. Отмена не меняет рабочую модель. При переключении объекта панель сбрасывает активную возможность.
- `plugin.gd` — жизненный цикл EditorPlugin, координация представлений и работа с EditorInterface. Он не должен повторно создавать внутренние контролы библиотеки или структуру вкладок редактора.

Представления общаются с контроллером через сигналы и небольшой публичный API. Они не читают файлы библиотеки, не меняют ObjectDefinition и не содержат runtime-логику.

### 2.1.1. Library, wizard and scene draft services

- `controllers/library_controller.gd` — загружает определения/шаблоны, строит поисковый индекс, фильтрует и сортирует записи, формирует карточки/панель сведений, управляет избранным, недавними и пользовательскими коллекциями. В поисковый индекс входят выбранные возможности, их keywords/описания, обязательные зависимости и пользовательские свойства.
- `services/library_actions_service.gd` — выполняет независимое дублирование, создание шаблона, переименование, безопасное удаление с резервной копией, проверку общих сцен и экспорт `.tres`. Не управляет UI и не обращается к `EditorInterface`.
- `services/object_creation_service.gd` — создаёт черновики с нуля, из шаблонов/объектов и через импорт сцены. Назначает новые ID и применяет пользовательские метаданные; запись определения в библиотеку остаётся отдельной явной операцией Save.
- `services/scene_draft_service.gd` — создаёт базовую PackedScene, клонирует сцену объекта и импортирует `.tscn`/`.scn` в отдельный путь. При импорте работает с временным экземпляром, сохраняет неизвестные узлы/скрипты/ресурсы и существующий `ObjectProperties`, проверяет 2D-корень и не перезаписывает исходник/занятый путь.
- `services/scene_node_dependency_service.gd` — read-only сканер ссылок перед удалением поддерева сцены: NodePath-свойства, реальные signal connections, AnimationPlayer tracks и ID/path-ссылки декларативной структуры ObjectDefinition. Он не изменяет сцену; UI использует результат для подтверждения.
- `ui/dialog_view.gd` — содержит единый мастер создания: выбор способа, необязательный профиль, категорию, имя, теги, описание и источник/файл импорта. Подсказки от исходника не перезаписывают вручную изменённые поля.
- `ui/library_details_view.gd` и `ui/library_action_dialogs.gd` — отдельные представления контекстных сведений и подтверждающих/редактирующих диалогов библиотеки.

Граница ответственности: `LibraryController` отвечает за состояние и поиск; сервисы — за операции над данными/сценами; UI — за отображение и пользовательский ввод; `plugin.gd` связывает их с вкладкой и API редактора. Сервисы создания и импорта не должны обращаться к `EditorInterface`.

### 2.2. Object System Runtime

Путь: scripts/object_system/

Отвечает за:
- загрузку определений и сцен;
- создание экземпляров;
- применение свойств и переопределений;
- запуск компонентов и возможностей;
- обработку событий и состояний;
- связи между объектами;
- совместимость версий.

Runtime не зависит от UI, EditorPlugin или редакторских singleton-объектов.

### 2.3. Object Library

Путь: data/object_library/

Хранит:
- определения объектов;
- сцены объектов;
- шаблоны;
- пользовательские категории и коллекции;
- миниатюры;
- индекс библиотеки и версии.

Библиотека не привязана к одной игровой сцене и должна переноситься между проектами вместе с зависимостями.

### 2.4. Extension Registry

Реестр регистрирует:
- возможности, доступные в простом режиме;
- внутренние типы компонентов;
- профили создания;
- типы свойств и редакторы полей;
- события, условия и действия;
- валидаторы и команды Preview.

Стороннее расширение предоставляет не только технический класс, но и карточку для пользователя: название, иконку, простое описание, настройки и подсказки.

## 3. Модель объекта

Объект хранит следующие данные:

- **Object Definition:** постоянный object_id, имя, категория, теги, описание, версия.
- **Object Scene:** настоящая PackedScene Godot с узлами, графикой, физикой, анимациями, аудио и частями.
- **Appearance Data:** сведения, необходимые простому визуальному редактору.
- **Capability Selections:** выбранные пользователем возможности.
- **Component Bindings:** внутренние привязки компонентных реализаций к узлам.
- **Property Definitions:** стабильные ID, типы, подписи, значения, диапазоны и подсказки.
- **Behavior Data:** состояния, события, условия и действия.
- **Object Links:** ссылки на другие объекты и точки крепления.
- **Preview Data:** миниатюра и параметры Preview.
- **Dependencies:** изображения, аудио, сцены, ресурсы, скрипты и другие объекты.

Базовое определение не смешивается с временным Preview-состоянием и игровым состоянием экземпляра.

## 4. Возможность — понятная оболочка над технической реализацией

Это ключевой слой между простым интерфейсом и внутренними компонентами.

У каждой возможности есть:
- стабильный capability_id;
- пользовательское название, иконка и описание;
- короткий пример результата;
- группа и поисковые слова/синонимы;
- список требуемых внутренних компонентов и узлов;
- схема обычных настроек с понятными подписями;
- значения по умолчанию;
- зависимости и несовместимости;
- правила установки, обновления и удаления;
- события/действия, доступные другим возможностям;
- Preview-адаптер и валидаторы;
- версия и миграция.

Пример: пользователь нажимает «Можно подобрать». Карточка возможности знает, какие узлы/компоненты нужны, какие свойства показать и как проверить результат. Пользователь не должен выбирать компонент подбора вручную.

### 4.1. Установка возможности

Установка должна быть транзакционной и обратимой:

1. Проверить совместимость с текущим объектом.
2. Определить отсутствующие зависимости.
3. Показать пользователю короткое объяснение, если требуется дополнительная возможность.
4. Сформировать план изменений.
5. Применить его одной Undo/Redo-операцией.
6. Обновить список настроек и Preview.
7. Провести проверку и показать понятный результат.

Нельзя молча добавлять большое количество неожиданных систем. Нельзя молча менять целевой узел. Конфликт должен приводить к понятному выбору или диагностике.

## 5. Внутренняя компонентная модель

Разделить три сущности:

- **Component Type** — описание реализации, например Health, Audio или Interactable.
- **Component Binding** — привязка реализации к узлу объекта с настройками.
- **Runtime Instance** — работающий компонент в игре.

Binding хранит binding_id, component_type_id, target node ID или NodePath, enabled, settings, component_version и источник пакета. Если порядок исполнения нужен, он задаётся отдельно и явно.

Привязка должна поддерживать любой подходящий узел, а не только корень объекта. Например, звук может относиться к аудио-части, hitbox — к Area2D, а визуальный эффект — к отдельному дочернему элементу.

Если явно заданный target отсутствует, система выдаёт ошибку. Запрещено без предупреждения переносить компонент на корень.

Для старых определений, где компоненты были на корне, требуется совместимое чтение и безопасная миграция.

## 6. Пользовательские свойства

Свойства отделены от их экранных подписей.

Схема поля содержит:
- property_id;
- название и описание простым языком;
- тип;
- значение по умолчанию;
- группу;
- уровень сложности;
- min/max/step для чисел;
- варианты для Enum;
- условия отображения;
- правила сериализации.

Внутренние компоненты ссылаются на property_id, а не на отображаемую подпись.

Простой режим показывает понятные значения: «Здоровье», «Скорость», «Урон», «Вместимость». Расширенный режим может открыть точные типы, ID, группы и технические параметры.

Целевые типы: Boolean, Integer, Float, String, Enum, Vector2, Vector3, Color, Texture2D, AudioStream, PackedScene, Resource, Array, Dictionary и ссылка на узел в поддерживаемом контексте.

## 7. Профили и категории

Категория — метаданные для библиотеки, поиска и фильтрации. Она не ограничивает поведение объекта.

Профиль — необязательная стартовая конфигурация. Он может предложить базовую структуру, внешний вид, возможности и свойства. Пользователь может изменить или удалить любое предложение.

Профили хранятся как ресурсы или пакеты и регистрируются через Extension Registry. Не держать все профили в жёстко зашитом словаре центрального plugin.gd.

## 8. Визуальный редактор

Основное поле отображает объект и его части. Оно должно поддерживать:
- загрузку изображений и ресурсов;
- выбор части кликом;
- перемещение, вращение и масштаб;
- добавление и удаление частей;
- кадры и анимации;
- визуальное редактирование коллизий;
- origin/pivot и именованные точки крепления;
- привязку к сетке и Undo/Redo.

В простом режиме показываются только доступные сейчас действия. Сетки, sockets, hitbox/hurtbox, точные слои и другие технические наложения включаются по запросу.

Не нужно переписывать весь 2D-редактор Godot с нуля. Использовать стандартные ресурсы и механизмы Godot, добавляя удобные сценарии поверх них.

## 9. Preview

Preview создаёт временный экземпляр актуального черновика. Он не перезаписывает Definition, World или игровые сохранения.

Preview поддерживает постепенно добавляемые адаптеры для внешнего вида, анимаций, коллизий, взаимодействий, звуков, урона, разрушения, дропа и других возможностей.

Если возможность пока нельзя проверить в Preview, интерфейс явно сообщает об этом. Нельзя показывать ложный статус «Проверено».

Для автоматических runtime-проверок использовать headless smoke-тесты и тестировать реальные классы/методы напрямую. Не добавлять тестовые .tscn-манекены только для проверки математики или простых API.

## 10. Библиотека, экземпляры и обновления

Рекомендуемая структура:
- addons/object_builder/ — редактор.
- scripts/object_system/ — runtime.
- data/object_library/objects/ — определения и сцены.
- data/object_library/templates/ — шаблоны.
- data/object_library/categories/ — категории.
- data/object_library/collections/ — коллекции.
- data/object_library/previews/ — миниатюры.
- data/object_library/library_index.tres — восстанавливаемый индекс.

Definition — исходный объект. Template — основа для создания копии. Instance — размещённый или созданный runtime объект. Instance Override — собственная настройка экземпляра.

Экземпляр хранит исходный ID и базовую версию. Обновление Definition не должно автоматически перезаписывать все экземпляры. Перед обновлением пользователь видит изменения и конфликты. Предусмотреть выборочное обновление, отвязку и резервное копирование.

## 11. Ошибки и безопасность

Внутренние диагностики имеют машинно-читаемый код, контекст, серьёзность и место исправления.

Простой UI отображает понятные сообщения и действия. Расширенный UI может показать технический текст, NodePath, ID и лог.

Все изменения поддерживают Undo/Redo. Перед миграциями и массовыми операциями создаётся backup. Неизвестные поля и расширения не удаляются при сохранении.

## 12. Текущее состояние реализации

**Текущая версия: Object Builder 0.8.0-dev.**

Реализовано:
- editor dock с библиотекой, поиском и фильтрами;
- мастер с 12 стартовыми профилями, пунктом «Без профиля» и шаблонами;
- ObjectDefinition schema 5, отдельные определения/сцены, резервные копии и пользовательские свойства;
- ObjectProperties и синхронизация со штатным Inspector;
- панели Sprite2D и AnimatedSprite2D;
- единый Component Catalog: встроенные Health, Damageable, Attack, Destructible, Pickup и Interactable, а также пользовательская регистрация;
- ObjectSceneStructureService: декларативное построение дочерних узлов, проверка родительского графа, типов и свойств, установка групп/метаданных и соединение сигналов; при ошибке создаваемые узлы удаляются;
- capability settings schema: формирование настроек из определений компонентов с уровнями Basic / Advanced / Expert, валидацией обязательных полей и подтверждением плана изменения;
- MechanicModuleLoader API v1: загрузка десяти независимых пакетов механик по module.cfg в редакторе и runtime;
- проверка supported_node_types, required/incompatible components и разрешение Component Bindings до создания объекта;
- Capability Definition / Selection / Catalog / Service, типизированные requires/conflicts, транзитивные зависимости и проверка циклов/несовместимостей;
- CapabilityCatalogController и CapabilityBatchPlanner обеспечивают независимое многократное выделение и атомарный preview-план; commit всего набора остаётся одним действием EditorUndoRedoManager в plugin;

## 14. Критерии качества

- Простой объект можно создать и разместить без знания Godot.
- Для типовых возможностей не требуется вручную добавлять узлы и соединять сигналы.
- Пользователь всегда понимает, что произойдёт после нажатия кнопки.
- Параметры появляются по контексту, а не все сразу.
- Простой и расширенный режимы редактируют один объект.
- Категории не ограничивают комбинации возможностей.
- Runtime работает без включённого editor-плагина.
- Автоматические проверки не засоряют проект демонстрационными сценами.

## Целевая архитектура умного каталога возможностей

Каталог строится поверх существующих ObjectCapabilityDefinition, ObjectCapabilityCatalog, ObjectCapabilityService и MechanicModuleLoader. Новые сервисы добавляются только там, где текущие контракты не покрывают задачу; не создавать дублирующие реестры без необходимости.

### Классификация и исполнение

Модель возможности должна разделять независимые поля:
- kind_id — расширяемый тип назначения (presentation, animation, audio, physics, movement, interaction, combat, inventory, resources, state, logic, lifecycle, data, networking, custom и т. п.);
- execution_scope — editor_only, runtime, hybrid или data_only;
- implementation_type — scene/resource configuration, declarative data, component, node/signal setup, runtime service или extension;
- readiness_status — реализована ли вся необходимая часть именно для выбранной области действия.

Эти поля нельзя смешивать с пользовательской категорией каталога или профилем объекта. Не каждая возможность требует runtime-компонента. Валидация готовности должна проверять соответствующий способ реализации, сериализацию, миграции и smoke-тесты.

### Метаданные и отношения

Определение/метаданные возможности должны содержать постоянный ID, локализуемое имя и описание, категорию и теги, синонимы, примеры запросов, ссылки на иконку и подробную иллюстрацию, область действия, статус, схему настроек, ограничения совместимости и версию схемы.

Отношения имеют тип, целевой ID, объяснение, опциональное условие и источник/версию. Поддерживаемые типы: requires, recommends, extends, alternative, conflicts, related. Обязательные зависимости остаются машиночитаемыми и участвуют в планировщике; рекомендации и тематические связи не должны автоматически подключать механики. Конфликты должны иметь реальное техническое основание и объяснение.

### Сервисы и ответственность

Целевые обязанности:
- каталог/реестр — регистрация, поиск по ID, проверка уникальности и версий;
- поисковый сервис — локальный поиск по текстовым полям, синонимам и примерам;
- сервис рекомендаций — контекстное ранжирование с объяснением причины;
- сессия выбора — независимый от фильтров и поисковой выдачи список выделенных ID;
- batch planner — проверка набора, транзитивных зависимостей, дубликатов и конфликтов, выдача неизменяемого плана;
- batch apply service — атомарное применение плана, сохранение пользовательских настроек и одна Undo/Redo-команда;
- представление связей — локальный граф для UI; данные отношений хранятся отдельно от отрисовки.

Это логические обязанности, а не обязательный список файлов. При реализации сначала проверить существующие сервисы и расширить их, если это проще и чище. plugin.gd не должен содержать поиск, рекомендации, разрешение зависимостей и отрисовку графа.

### Пакетное применение

План должен явно различать user_selected, auto_required, already_present и blocked/conflicting. Общие зависимости добавляются один раз. Валидация выполняется до изменения объекта. Применение — транзакционное: либо все изменения фиксируются, либо состояние остаётся прежним. Автоматические зависимости сохраняют происхождение; пользовательские записи нельзя молча удалять при очистке зависимостей.

### Визуальные ресурсы

Иконки/иллюстрации регистрируются по постоянному ID возможности, а не по индексу карточки или отображаемому имени. Нужны проверка существования ресурсов, fallback-заглушка и отдельный статус визуальной готовности. Представление карточки не должно быть жёстко связано с типом исполнения.


## Фактически внедрённая модель метаданных возможностей

ObjectCapabilityDefinition расширен полями kind_id, execution_scope, implementation_type, readiness_status, icon_resource_path, illustration_resource_path, synonyms, example_queries, relations и compatibility_rules.

- kind_id описывает назначение возможности и не заменяет пользовательскую категорию.
- execution_scope описывает, действует ли возможность в редакторе, в игре, на обоих этапах или только задаёт данные.
- implementation_type не предполагает, что каждая запись обязана создавать runtime-компонент.
- readiness_status отделён от legacy runtime_status. Метод is_ready() поддерживает старые ресурсы, а явный новый статус имеет приоритет.
- ObjectCapabilityCatalog заполняет безопасные значения по категориям и проверяет типизированные отношения: requires, recommends, extends, alternative, conflicts и related. Каждая связь обязана ссылаться на существующий ID и иметь объяснение.
- ObjectCapabilityService и карточный список используют общий readiness API. Новая схема допускает готовые editor-only/data-only возможности без runtime-компонентов.

Это пока фундамент данных. Большинство иконок/иллюстраций, синонимов, примеров, связей и индивидуальных областей действия в каталоге ещё предстоит заполнить и проверить. Умный поиск, рекомендации, полноценный множественный выбор и атомарный пакетный план ещё не реализованы.
