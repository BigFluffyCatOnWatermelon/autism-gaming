# Архитектура Object Builder

## Главный принцип

Редакторский плагин, библиотека определений и runtime-исполнение — три независимых слоя. Выключение Object Builder не должно ломать игру или загрузку уже созданных объектов.

## Слои

### 1. Object Builder — editor-only

Путь: addons/object_builder/

Задачи плагина: навигация по категориям, поиск, формы метаданных, редактор пользовательских свойств, запуск стандартного редактора сцен. Плагин не содержит боевую логику и не управляет игровыми экземплярами.

Интерфейс остаётся компактным: слева поиск, переключение Все/Избранное/Недавние, категория, тег и список объектов; справа свойства выбранного объекта и сгруппированные области. Избранное и недавние ID хранятся через EditorSettings project metadata вне папки проекта, поэтому пользовательские предпочтения не попадают в Git.

Плагин показывает дерево только если в редакторе открыта сцена, чей scene_file_path совпадает со scene_path выбранного определения. Это защищает от случайного изменения другой сцены. Добавление и удаление узлов регистрируются в EditorUndoRedoManager и входят в общую историю Ctrl+Z/Ctrl+Y. Сохранение сцены остаётся обычным действием редактора (Ctrl+S).

### 2. Object System — runtime

Путь: scripts/object_system/

- ObjectDefinition — Resource-описание объекта и версия схемы.
- ObjectPropertyDefinition — ID, отображаемое имя, тип, значение по умолчанию, группа и описание пользовательского свойства.
- ObjectComponentDefinition — подключаемый компонент, его скрипт и настройки.
- ObjectComponent — базовый Node-контракт для runtime-компонентов.
- ObjectFactory — создание экземпляра из сцены или типа корневого узла, применение значений и компонентов.
- ObjectRegistry — поиск определений и создание объектов по постоянному ID.

Runtime не зависит от EditorPlugin и может использоваться при выключенном плагине.

### 3. Object Library — данные

Путь: data/object_library/

- objects/<id>.tres — определения объектов.
- templates/<id>.tres — шаблоны.
- scenes/<id>.tscn — сцены объектов.
- Категория и теги хранятся внутри определения; список пользовательских категорий не зашит в формат файла.

## Идентичность и данные

Постоянный object_id — ключ для ссылок и будущих сохранений. Отображаемое название, категория, описание и теги можно менять. Пользовательское свойство имеет собственный property_id; подпись в UI не используется как ключ.

Пользовательские свойства в 0.1.0 сохраняют типизированные значения String, Integer, Float, Boolean и Vector2. Runtime хранит их в метаданных экземпляра через ObjectFactory API. Следующий этап — адаптеры к сериализованным полям игровых компонентов и контролы свойств в полноценном инспекторе.

## Компоненты

Компонент описывается через ObjectComponentDefinition и реализуется скриптом, наследующим ObjectComponent. Компонент получает настройки через configure(Dictionary). Это позволяет добавлять Health, Damageable, Harvestable, DropTable, Audio и другие функции независимо от конкретного типа объекта.

Первая версия содержит контракт и фабрику, но не полноценный каталог игровых компонентов и не редактор их настроек. Базовое дерево сцены добавляет стандартные узлы Godot, но пока не редактирует их свойства внутри собственного инспектора: для этого используется штатный Inspector.

## Определение, шаблон и экземпляр

Общее определение хранится в библиотеке; шаблон хранится отдельно и используется для создания независимой копии. Размещённый в сцене объект или созданный в игре узел — экземпляр. Изменение экземпляра не должно молча менять исходное определение.

Для дальнейшего развития нужны overrides, связь с версией определения, команды «обновить выбранные экземпляры», «отвязать» и предварительный просмотр изменений.

## Версии и восстановление

- Версия схемы данных отделена от версии плагина.
- Новая версия плагина должна читать старые определения либо предоставлять явную миграцию.
- Перед изменением существующего определения создаётся резервная копия .bak.
- Неизвестные поля и компоненты сохраняются; неизвестный скрипт компонента пропускается с предупреждением, а не удаляет данные.
- Автоматическое преобразование игровых ResourceNode и Cozy Village сцен запрещено без отдельной проверки и копии.

## Границы 0.1.0

Сейчас реализованы создание пустых объектов и копий из шаблонов, базовые 2D root-типы, категории/поиск, метаданные, пользовательские свойства и runtime-фабрика/реестр. Шаблоны пока содержат только начальные параметры и сцену-заготовку. Встроенный node-tree editor, предпросмотр, редактор компонентов, наследование и миграции — следующие этапы.
