# План унификации настроек игровых механик

> Рабочий документ для рефакторинга настроек механик активного плагина Web Object Builder. Чек-лист отражает состояние, зафиксированное в проектной документации на момент создания файла.

## 1. Цель

Привести настройки всех игровых механик к единой, понятной и визуальной системе. Пользователь должен подключать механику к объекту, открывать её настройки и работать с обычными элементами интерфейса: переключателями, числовыми полями, списками, каталогами предметов и объектов, таблицами и специализированными визуальными редакторами.

Пользователь не должен вручную вводить технические JSON-структуры, внутренние ID компонентов или служебные значения, чтобы настроить обычное игровое поведение.

Итоговая модель:
1. У объекта есть единый список подключённых пользовательских механик.
2. Каждая механика представлена одной карточкой/строкой с названием и кратким состоянием.
3. Выбор механики открывает её настройки в одном и том же контекстном инспекторе.
4. Настройки сгруппированы по смыслу и используют общий набор контролов.
5. Вложенные возможности настраиваются внутри родительской механики, а не дублируются отдельными карточками.
6. Технические компоненты, схемы хранения и JSON остаются внутренней реализацией, а не пользовательским интерфейсом.

## 2. Обязательные UX-правила

- **Один способ настройки.** Не должно быть нескольких конкурирующих мест для редактирования одной механики.
- **Одна карточка на одну пользовательскую механику.** Внутренние компоненты и дочерние возможности не засоряют общий список.
- **Настройки рядом с названием.** Выбор механики открывает её параметры в контекстной панели; не нужно искать отдельные технические вкладки.
- **Общие правила интерфейса.** Одинаковые типы данных выглядят и работают одинаково во всех механиках.
- **Без ручного JSON.** JSON-поля, массивы ID и словари не показываются как обычные текстовые поля. Для них создаются визуальные редакторы.
- **Выбор вместо ввода ID.** Предметы, объекты, таблицы, сцены, анимации и ресурсы выбираются из каталогов с поиском и понятными названиями.
- **Сложные данные — отдельный редактор.** Таблицы добычи, рецептов, производства, маршруты и наборы эффектов редактируются в специализированных списках/окнах.
- **Basic по умолчанию.** Часто используемые параметры видны сразу; Advanced и Expert скрыты до запроса пользователя.
- **Без дублирования состояния.** Одно игровое значение имеет один источник истины.
- **Без потери совместимости.** Старые объекты и ключи настроек мигрируют с сохранением прежнего поведения.
- **Не скрывать незавершённость.** Наличие карточки или возможность сохранить настройку не означает, что механика полностью подключена к игровому циклу.

## 3. Целевая структура редактора

### 3.1 Список подключённых механик

Показывать только пользовательские механики, подключённые к объекту. Для каждой строки:
- название и короткое описание;
- состояние включения;
- предупреждение о незаполненных обязательных параметрах или отсутствующих ссылках;
- действие открытия настроек;
- отключение/удаление с подтверждением, если действие может повлиять на данные.

Не показывать в обычном списке низкоуровневые runtime-компоненты, скрытые дочерние возможности, технические ID и имена скриптов, а также дублирующие карточки одной функции.

### 3.2 Единая панель настроек механики

Все механики используют общий каркас:
1. Заголовок, описание и общий переключатель активности.
2. Основные настройки, открытые сразу.
3. Смысловые группы параметров.
4. Расширенные настройки, свёрнутые по умолчанию.
5. Экспертные/служебные параметры только в расширенном режиме.
6. Контекстные предупреждения и ошибки.
7. Общие правила сохранения и отмены.

Не создавать уникальный интерфейс для каждой механики, если задача решается стандартными контролами. Специальный редактор допустим для сложного составного значения.

### 3.3 Общий набор контролов

| Тип значения | UI-контрол |
|---|---|
| Включено/выключено | Переключатель |
| Целое/дробное число | Числовое поле с ограничениями |
| Диапазон | Ползунок и/или два числовых поля |
| Процент | Поле/ползунок с обозначением % |
| Время, задержка, расстояние, радиус | Поле с единицами измерения |
| Перечисление | Выпадающий список с понятными названиями |
| Ссылка на предмет/объект | Каталог с поиском и предпросмотром |
| Ссылка на ресурс/таблицу | Выбор ресурса с проверкой типа |
| Цвет | Палитра |
| Вектор/точка | Визуальный редактор координат |
| Список записей | Повторяемые строки с добавлением, удалением и перестановкой |
| Добыча/рецепт/производство | Специализированный редактор таблицы |
| Маршрут/патруль | Редактор точек/узлов |
| Условия и действия | Визуальный конструктор правил |
| Анимация/звук/эффект | Выбор ресурса с предпросмотром |
| Сложная структура | Отдельное окно, а не сырой JSON |

Для каждого контрола определить единые правила валидации, отображения ошибок, значений по умолчанию, очистки и отмены.

## 7. Правила разработки

### 7.1 Архитектура и источники истины

1. Активный плагин — addons/web_object_builder. Архивный addons/object_builder не использовать для новых изменений.
2. Каталог возможностей и компонентные определения должны оставаться согласованными.
3. MechanicModuleLoader регистрирует модули; манифесты должны соответствовать ID, возвращаемым методами регистрации.
4. Runtime-компоненты отвечают за игровую логику; UI отвечает за редактирование и отображение. Не переносить игровую логику в JavaScript.
5. У каждой настройки один канонический ключ и один источник истины.
6. Не хранить одну функцию одновременно как независимую механику и как дублирующую вложенную настройку без явной миграции.
7. Скрытие карточки не означает удаление ID или отказ от поддержки старых сохранений.

### 7.2 Интерфейс

1. Не добавлять уникальные формы для стандартных типов данных.
2. Не показывать пользователю внутренние component ID, capability ID, имена скриптов и сериализованные словари.
3. Не просить вручную вводить item_id, если предмет можно выбрать из каталога.
4. Не выводить сырой JSON в обычном режиме.
5. Не дублировать настройку во вкладках механики, компонента и связей.
6. Не смешивать пользовательские механики с низкоуровневыми runtime-компонентами.
7. Подписи, подсказки, единицы измерения и ошибки должны быть понятны без знания внутренней архитектуры.
8. Сохранять компактность: длинные и редко используемые настройки сворачивать; сложные редакторы открывать по запросу.
9. Учитывать узкую ширину и малую высоту окна.

### 7.3 Форматы данных и JSON

1. JSON допустим как внутренний формат хранения, сериализации, обмена или диагностики.
2. JSON не является пользовательским редактором настроек.
3. Составные структуры редактировать визуально и сериализовать программно.
4. Не удалять существующий JSON-формат до реализации миграции и проверки старых объектов.
5. Не менять формат сохранения без версии/миграции, если это затрагивает существующие данные.
6. Не терять неизвестные поля и дополнительные метаданные при чтении и повторной записи.
7. Для ссылок использовать типизированные ресурсы/ID с выбором из каталога и валидацией.

### 7.4 Изменение механик

Перед изменением механики:
- определить её пользовательский смысл;
- найти capability definition, component definition, runtime-компонент и места использования;
- проверить, нет ли эквивалентной настройки;
- определить зависимости и конфликтующие поля;
- определить миграцию старых ключей;
- определить способ визуального редактирования;
- обновить документацию и чек-лист.

После изменения:
- проверить регистрацию и согласованность ID;
- проверить сериализацию и обратную совместимость;
- проверить, что выключенная вложенная функция действительно не выполняется;
- проверить, что новое UI-значение доходит до runtime, если механика заявлена как интегрированная;
- отмечать статус только по фактически выполненному объёму.

### 7.5 Тестирование и проверка

- Не использовать GitHub Actions для проверки Godot.
- Не добавлять и не запускать GitHub Actions/workflow-проверки Godot в рамках этого плана.
- Не выдавать smoke/headless-проверку за GUI-приёмку.
- Не утверждать, что поведение проверено в Godot, если запуск в настольном редакторе не выполнялся.
- Статический анализ не заменяет ручную проверку интерфейса и runtime.
- В документации различать статусы: реализовано, проверено по исходникам, проверено в runtime, проверено вручную в GUI.
- Если настольный Godot недоступен, оставить приёмку открытой и описать ограничение.
