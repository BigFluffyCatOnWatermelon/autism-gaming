# autism-gaming

Браузерная 2D-игра, которую мы разрабатываем небольшими итерациями вместе с ChatGPT.

> **Текущее состояние:** настроен стартовый проект Phaser 4 + JavaScript + Vite. В браузере доступна нейтральная техническая сцена для проверки движка и управления. Жанр и игровые механики ещё не определены.

## Ссылки

- **Открыть проект в StackBlitz:** https://stackblitz.com/github/BigFluffyCatOnWatermelon/autism-gaming
- **StackBlitz:** https://stackblitz.com/

GitHub — главный источник кода. StackBlitz открывает публичный репозиторий в браузере, устанавливает зависимости и запускает скрипт `dev`. Новые коммиты в GitHub автоматически отражаются в соответствующем открытом проекте StackBlitz.

В нашем рабочем процессе ChatGPT вносит изменения прямо в GitHub, а пользователь использует StackBlitz для запуска и проверки игры. Не создавай отдельные несвязанные копии проекта без необходимости.

## С чего начинать в новом чате

## Технологический стек

Стек проекта зафиксирован:

- **Phaser 4.2.1** — игровой движок для 2D.
- **JavaScript (ES modules)** — основной язык.
- **Vite 8.3.5** — dev-сервер и production-сборка.
- **StackBlitz WebContainers** — браузерная среда разработки и запуска.
- **GitHub** — хранение исходников и истории изменений.

Зависимости зафиксированы в `package.json`. Не обновляй их версии без причины: сначала проверь совместимость и необходимость обновления.

## Запуск в браузере

1. Открой: https://stackblitz.com/github/BigFluffyCatOnWatermelon/autism-gaming
2. Дождись загрузки проекта и установки зависимостей.
3. StackBlitz должен автоматически выполнить `npm run dev`.
4. Открой вкладку Preview, если она не появилась сама.
5. Для локальной проверки после будущих изменений используй обновление Preview.

В проекте также доступны команды:

- `npm run dev` — запуск dev-сервера.
- `npm run build` — production-сборка.
- `npm run preview` — просмотр production-сборки.

Node.js для Vite должен быть версии 20.19+ или 22.12+. В StackBlitz среда предоставляется браузером автоматически, устанавливать Node.js на компьютер пользователя не нужно.

### Если StackBlitz не запускается

WebContainers лучше всего работают в настольных Chromium-браузерах. В настройках браузера не должны блокироваться Service Workers и хранилище сайтов для StackBlitz. При проблемах попробуй открыть проект в отдельной вкладке и разрешить для StackBlitz необходимые данные сайта.

## Текущая техническая сцена

Пока это не настоящая игровая механика и не утверждение будущего дизайна. Сцена нужна для проверки среды:

- Phaser создаёт игровое окно.
- Масштабирование подстраивает сцену под размер Preview.
- Тестовый светящийся объект перемещается клавишами WASD или стрелками.
- Клавиша R возвращает объект в центр.
- Поле и интерфейс нарисованы средствами Phaser, внешние ресурсы пока не нужны.

## Основные требования проекта

- Игра двухмерная (2D).
- Разработка и запуск должны быть доступны через браузер.
- Не требовать от пользователя установки игрового движка, IDE или среды разработки на компьютер.
- Использовать существующие зависимости и архитектуру, не усложнять проект без необходимости.
- Учитывать, что пользователь работает с бесплатной версией ChatGPT: экономить контекст, избегать ненужных больших переписываний и решать задачи небольшими законченными порциями.

## Правила работы ChatGPT с кодом

### 1. Сначала изучить проект

- Перед изменениями прочитать документацию и изучить относящиеся к задаче исходники.
- Не предполагать, что проект пустой или устроен так же, как в прошлом чате: проверять текущее содержимое репозитория.
- Использовать уже существующие решения и зависимости, если они подходят.
- Не создавать второй механизм, если нужный уже существует.

### 2. Делать небольшие законченные изменения

- Реализовывать задачу минимальным набором изменений.
- Не переписывать работающие части проекта ради косметики или личных предпочтений.
- Не менять несвязанные механики, интерфейс, настройки и структуру.
- Не удалять существующие возможности без прямой просьбы пользователя.
- Не добавлять библиотеки и зависимости без реальной необходимости.
- Если задача затрагивает несколько систем, разделять её на понятные этапы.

### 3. Сохранять качество кода

- Писать понятный, поддерживаемый и разбитый на логические модули код.
- Избегать гигантских файлов и дублирования логики.
- Учитывать разные размеры окна браузера и масштаб игрового поля.
- Обрабатывать ошибки и пограничные случаи.
- Не хранить секреты, токены и приватные ключи в репозитории.
- Не добавлять тяжёлые ресурсы без необходимости; учитывать размер и производительность.

### 4. Проверять результат

После каждого изменения:

- Проверить синтаксис и сборку, если соответствующие команды доступны.
- Запустить игру в StackBlitz, когда это возможно.
- Проверить затронутую механику и связанные с ней функции.
- Проверить консоль браузера на ошибки, если доступна.
- Не писать, что задача проверена, если фактическая проверка не выполнялась.
- Если проверить что-либо не удалось, прямо указать это и объяснить, что нужно проверить пользователю.

### 5. Обязательно вести документацию

После **каждой завершённой задачи, меняющей проект**:

- Обновить `PROJECT_STATE.md`: что теперь реализовано, как это работает, какие решения приняты.
- Обновить `TASKS.md`: отметить завершённое и добавить обнаруженные следующие задачи.
- Добавить запись в `CHANGELOG.md`: дата, суть изменений, изменённые файлы и результат проверки.
- Обновлять этот README только при изменении общих правил, архитектуры или способа запуска.

Если задача не завершена, не отмечать её выполненной: записать текущий результат, оставшуюся работу и блокеры.

### 6. Git и сохранение изменений

- Сохранять изменения в GitHub небольшими логичными коммитами.
- Давать коммитам короткие понятные сообщения, например `feat: add player movement`, `fix: correct collision handling`, `docs: update project state`.
- Не перезаписывать чужие или пользовательские изменения, не проверив текущее состояние файлов.
- Не удалять историю и не использовать принудительный push без прямой необходимости и согласования.
- После сохранения указывать ссылку на коммит, если она доступна.

## Как описывать результат пользователю

После выполнения задачи сообщать:

1. Что именно изменено.
2. Какие файлы затронуты.
3. Что фактически проверено и с каким результатом.
4. Что осталось нерешённым или требует проверки в браузере.
5. Какие следующие задачи появились.

Не пересказывать весь проект при каждом небольшом изменении. Давать только важные сведения, чтобы экономить контекст.
