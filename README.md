# autism-gaming

Браузерная 2D-песочница, которую мы разрабатываем небольшими итерациями вместе с ChatGPT.

> **Текущее состояние:** базовая пиксельная песочница уже создана: травяной мир, персонаж с анимациями, камера, перекат, оружие, хотбар, инвентарь, настройки и F3-отладчик. Сейчас это основа для дальнейшей игры, а не законченный игровой цикл.

## Технологический стек

- **Phaser 4.2.1** — игровой движок для 2D.
- **JavaScript (ES modules)** — основной язык.
- **Vite 8.3.5** — dev-сервер и production-сборка.
- **StackBlitz WebContainers** — браузерная среда разработки и запуска.
- **GitHub Actions** — автоматические тесты логики и production-сборка.
- **GitHub** — хранение исходников и истории изменений.

Версии зависимостей зафиксированы в `package.json`. Не обновляй их без причины.

## Запуск в браузере

1. Открой: https://stackblitz.com/github/BigFluffyCatOnWatermelon/autism-gaming
2. Дождись загрузки проекта и установки зависимостей.
3. StackBlitz должен выполнить `npm run dev`.
4. Открой вкладку Preview, если она не появилась автоматически.

Команды проекта:

- `npm run dev` — запуск dev-сервера.
- `npm test` — тесты боевой математики.
- `npm run build` — production-сборка.
- `npm run preview` — просмотр production-сборки.

Node.js для Vite должен быть версии 20.19+ или 22.12+. В StackBlitz среда предоставляется WebContainers, устанавливать Node.js на компьютер пользователя не нужно.

## Текущее состояние игры

### Мир

- Пустой мир 3600×3600 мировых пикселей.
- Повторяющаяся пиксельная трава и небольшие декоративные пиксели.
- Границы мира ограничивают перемещение.
- Трава рисуется слоем размером с экран, который прокручивается с камерой; не создавай огромный TileSprite размером со всю карту.

### Персонаж и камера

- Оригинальный спрайт 32×40, четыре направления и четыре кадра на направление.
- Отдельная тень.
- Ходьба, бег, приседание и перекат.
- Камера следует за персонажем с плавным сглаживанием.
- При беге обзор расширяется, при приседании камера приближается.
- Удары и перекаты могут вызывать тряску камеры.

### Оружие и типы урона

- Меч: ЛКМ — широкий режущий замах по сектору, ПКМ — колющий тычок по узкой линии.
- Кирка: колющий урон и повышенная эффективность по камню.
- Топор: режущий урон и повышенная эффективность по дереву и существам природы, например будущим энтам.
- Лук: выпускает стрелу в сторону курсора; расходует стрелы.
- У атак раздельные урон, перезарядка, дальность, расход выносливости и тип повреждения.
- Боевые цели пока не размещены в пустом мире. Система урона уже умеет принимать объекты с материалами `wood`, `stone`, `flesh` и `nature`.

Будущие деревья, камни и существа должны регистрироваться как боевые цели через `WorldScene.registerCombatTarget()`, а не добавлять отдельную формулу урона.

### Интерфейс

- Девять слотов быстрого доступа внизу экрана.
- Стартовые предметы: меч, кирка, топор, лук и стрелы.
- Инвентарь открывается клавишей B.
- Есть слоты брони: голова, тело, ноги и обувь.
- Рюкзак показывает 12 открытых и 12 закрытых ячеек. Закрытые ячейки — задел под будущие покупки в магазине.
- Отображаются здоровье, выносливость, характеристики персонажа и параметры выбранного оружия.
- Настройки сохраняются в localStorage текущего браузера.

### Отладчик и журнал

- F3 включает режим разработчика.
- Наведение на зарегистрированный объект подсвечивает его, клик выбирает объект в инспекторе.
- F2 открывает журнал; журнал также выводит события в консоль.
- Параметры сгруппированы по категориям и редактируются на лету.
- Для новых объектов можно использовать `WorldScene.registerDebugTarget()`.
- Для новых общих игровых параметров добавляй значения и описания в `src/config/gameConfig.js` и поля в `DEBUG_FIELDS`.
- Для индивидуальных параметров объекта регистрируй `fields` с `getValue` и `setValue`.

## Важное ограничение текущей версии

Это **базовый прототип механик**, не полноценная игра. Пока нет деревьев, камней, врагов, лута, экипируемых предметов брони, перетаскивания предметов, магазина, сохранения мира и звуков. Поэтому боевые атаки сейчас показывают эффекты и записываются в журнал, но реальных целей для нанесения урона пока нет.

## Правила работы ChatGPT с кодом

### 1. Сначала изучить проект

- Перед изменениями прочитать документацию и изучить относящиеся к задаче исходники.
- Не предполагать, что проект пустой или устроен так же, как в прошлом чате: проверять текущее содержимое репозитория.
- Использовать существующие решения и зависимости, если они подходят.
- Не создавать второй механизм, если нужный уже существует.

### 2. Делать небольшие законченные изменения

- Реализовывать задачу минимальным набором изменений.
- Не переписывать работающие части проекта ради косметики или личных предпочтений.
- Не менять несвязанные механики, интерфейс, настройки и структуру.
- Не удалять существующие возможности без прямой просьбы пользователя.
- Не добавлять библиотеки без реальной необходимости.
- Если задача затрагивает несколько систем, разделять её на этапы.

### 3. Качество кода и конфигурация

- Писать понятный, поддерживаемый, модульный и подробно прокомментированный код.
- Важные часто изменяемые параметры хранить в `src/config/gameConfig.js`, а не разбрасывать магические числа по коду.
- Делить конфигурацию по категориям: мир, игрок, камера, бой, оружие, инвентарь, настройки.
- У каждого настраиваемого параметра должна быть короткая поясняющая заметка.
- Параметры для F3 описывать в `DEBUG_FIELDS`, указывая подпись, описание, тип и допустимый диапазон.
- Избегать дублирования логики и не создавать гигантские файлы.
- Не хранить секреты, токены и приватные ключи в репозитории.

### 4. Объекты и отладка

- Новые интерактивные объекты должны использовать общие системы мира, урона и отладчика.
- Регистрировать доступные для инспектора объекты через `registerDebugTarget()`.
- Для боевых целей использовать `registerCombatTarget()`.
- Не создавать отдельную реализацию урона для каждого нового врага или ресурса.
- Обеспечивать выбор объекта мышью и редактирование его полей через F3.

### 5. Проверять результат

После каждого изменения:

- Запустить `npm test`, если затронута игровая логика.
- Проверить `npm run build` через GitHub Actions.
- Запустить игру в StackBlitz, когда это возможно.
- Проверить затронутую механику и консоль браузера.
- Не писать, что задача проверена, если фактическая проверка не выполнялась.

### 6. Документация и Git

После каждой завершённой задачи обновлять `PROJECT_STATE.md`, `TASKS.md` и `CHANGELOG.md`. Общие правила и команды отражать в README.

Сохранять изменения логичными коммитами. Перед обновлением файлов сверять текущие изменения и не перезаписывать чужую работу. Не использовать force push.

## Главное правило

**Репозиторий и его документация — источник истины о проекте.** Каждый новый чат сначала восстанавливает контекст из них, затем вносит минимальные необходимые изменения, проверяет результат и фиксирует его.
