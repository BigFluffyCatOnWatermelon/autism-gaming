# Object Builder — простота как принцип

**Главный тезис: «Сложность — внутри. Простота — снаружи».**

**Обещание плагина:** создавать игровые объекты должно быть так же просто, как собрать конструктор: выбрать внешний вид, добавить нужные возможности, настроить, попробовать и использовать.

Статус: целевая продуктовая и техническая спецификация. Godot 4.7.2, первая целевая версия — 2D. Это описание того, каким Object Builder должен стать; оно не означает, что все перечисленные возможности уже реализованы.

Документ дополняет авторские ROADMAP.md и OBJECT_BUILDER_SYSTEM_PLAN.md. Оригинальные документы сохранены без изменений. При расхождении старых UX-предложений с настоящей спецификацией для дальнейшей разработки Object Builder приоритет имеет этот документ и OBJECT_BUILDER_WORKFLOW.md.
Детальная карта интерфейса — OBJECT_BUILDER_UI_SPEC.md: структура каждого экрана, панели, кнопки, списки, поля, контекстные меню и состояния. Пользовательские сценарии — OBJECT_BUILDER_WORKFLOW.md. Очерёдность фаз, зависимости и критерии готовности — OBJECT_BUILDER_ROADMAP.md.

## 1. Для чего существует Object Builder

Object Builder — конструктор игровых объектов для людей, которые хотят создавать игру, а не изучать внутреннее устройство Godot.

Ребёнок или новичок должен суметь сделать простой игровой объект без программирования, без изучения документации и без необходимости знать технические названия узлов. Опытный разработчик при этом не должен упираться в потолок возможностей: все внутренние настройки остаются доступными в отдельном расширенном режиме.

**Плагин не должен упрощать возможности ценой ограничений. Он должен упрощать путь к этим возможностям.**

Три главных действия пользователя:

1. **Внешний вид** — показать конструктору, как объект выглядит.
2. **Возможности** — выбрать, что объект умеет делать.
3. **Настройки** — указать, как именно он это делает.

Дальше пользователь нажимает «Попробовать», проверяет результат и сохраняет объект.

Внутри плагин сам создаёт необходимые узлы, компоненты, связи, свойства и стандартную логику. Пользователю не нужно собирать эту техническую конструкцию вручную.

## 2. Правила простоты

Это обязательные правила проектирования интерфейса, а не пожелания.

1. **Сначала понятный результат, потом технические детали.** В простом режиме нельзя начинать работу с дерева узлов, классов Godot, компонентных привязок, NodePath или ID свойств.
2. **Один экран — одна понятная задача.** Не показывать десятки равнозначных кнопок и параметров одновременно.
3. **Использовать обычные слова.** «Можно подобрать», «Хранит предметы», «Получает урон», а не «Pickup Component», «Inventory Binding» или «Damageable».
4. **Показывать результат сразу.** Изменение изображения, размера, скорости или поведения должно быть понятно по предпросмотру.
5. **Автоматизировать техническую работу.** Если пользователь выбрал возможность «Можно подобрать», плагин сам готовит всё необходимое для подбора.
6. **Не задавать необязательные вопросы.** ID, базовые узлы, внутренние связи и начальные значения создаются автоматически. Категория и профиль используются как подсказки, а не как экзамен перед созданием.
7. **Объяснять действия заранее.** Если выбор добавит дополнительные возможности или потребует зависимости, коротко рассказать об этом человеческим языком.
8. **Всегда давать безопасный выход.** Undo/Redo, отмена, сброс предпросмотра и резервное копирование обязательны.
9. **Не путать простоту с примитивностью.** У каждой простой настройки может быть более точная экспертная настройка, но она не должна мешать новичку.
10. **Никакой привязки к одному виду объекта.** Один набор инструментов должен создавать предметы, ресурсы, оружие, персонажей, NPC, животных, снаряды, механизмы, здания, эффекты и пользовательские объекты.

## 3. Два уровня интерфейса

### 3.1. Простой режим — включён по умолчанию

Это основной продукт и основной путь разработки.

Пользователь видит:
- крупные карточки с картинками;
- понятные названия возможностей;
- визуальную рабочую область;
- привычные переключатели, поля и ползунки;
- только те настройки, которые относятся к текущему выбору;
- большую кнопку предпросмотра;
- понятные сообщения об ошибках с предложением исправления.

В простом режиме не показываются:
- классы и типы узлов Godot;
- внутреннее дерево сцены;
- Component Type, Component Binding и Runtime Instance;
- NodePath, property_id, component_id и прочие служебные идентификаторы;
- сырые словари, массивы и технические структуры;
- необходимость вручную соединять сигналы или писать код для обычных игровых задач.

Простой режим не ограничивает библиотеку возможностей. Пользователь по-прежнему может добавлять любые зарегистрированные возможности. Просто их внутренняя реализация скрыта.

### 3.2. Расширенный режим — по запросу

Переключатель «Расширенные инструменты» открывает доступ к:
- дереву сцены и настоящим узлам Godot;
- компонентам и их привязкам к конкретным узлам;
- полному набору пользовательских свойств и типов;
- событиям, условиям, переходам состояний и связям;
- техническим зависимостям;
- пользовательским GDScript и собственным ресурсам;
- точным параметрам физики, анимаций и визуальных частей.

Расширенный режим не заменяет простой и не становится обязательным этапом. Пользователь может включить его для одной задачи и вернуться обратно. Включение режима не должно менять сам объект или терять данные.

### 3.3. Постепенное раскрытие настроек

В простом режиме сначала показываются базовые параметры. Редкие настройки находятся под ссылкой или кнопкой «Дополнительно».

Настройки могут иметь уровни:
- **Основные:** нужны почти всем.
- **Дополнительные:** нужны для более точного поведения.
- **Экспертные:** технические возможности для особых случаев.

Не превращать это в три обязательных шага мастера. Пользователь открывает дополнительные настройки только тогда, когда сам этого хочет.

## 4. Главная навигация

Не создавать сложную панель из множества разделов верхнего уровня.

Основные места всего два:

**Библиотека**
- карточки объектов;
- поиск;
- категории и пользовательские коллекции;
- избранное и недавние;
- создание, копирование, импорт и удаление.

**Конструктор**
- текущий объект;
- внешний вид;
- возможности;
- настройки;
- предпросмотр;
- сохранение и добавление в игровую сцену.

Шаблоны доступны как фильтр или отдельная вкладка внутри библиотеки. Диагностика открывается только при наличии проблем или по запросу. Настройки самого плагина находятся в меню, а не занимают место на главном экране.

## 5. Сценарий создания: от пустого места до объекта

### Шаг 1. Нажать «Создать объект»

Плагин предлагает понятные способы:
- С нуля.
- Из готового шаблона.
- Сделать копию.
- Импортировать существующую сцену.

В обычном сценарии пользователь выбирает «С нуля».

### Шаг 2. Выбрать, что примерно создаём

Показываются крупные карточки с иллюстрациями: предмет, ресурс, оружие, инструмент, персонаж, NPC, животное, контейнер, механизм, постройка, эффект и «Другое».

Выбор помогает подобрать стартовые подсказки и начальные возможности. Это не жёсткий тип и не ограничение. Например, оружию можно добавить хранение предметов, интерактивность, разрушение или любые другие совместимые возможности.

Есть вариант «Не знаю» или «Обычный объект». Он позволяет продолжить без изучения категорий.

Пользователя не спрашивают о корневом узле Godot. Плагин выбирает техническую основу автоматически. Имя, постоянный ID и служебные метаданные создаются или запрашиваются в подходящий момент; обязательным остаётся только понятное имя объекта.

### Шаг 3. Добавить внешний вид

Пустая рабочая область показывает большие действия:
- Добавить изображение.
- Добавить ещё одну часть.
- Добавить анимацию.
- Изменить размер.

Пользователь может перетащить изображение из файловой системы, выбрать ресурс проекта или начать с пустого объекта.

Части объекта можно выбирать прямо мышью на изображении, перемещать, масштабировать и вращать. Например, у сундука отдельно двигается крышка, у персонажа — отдельные визуальные части, у механизма — движущаяся деталь.

Сетка, точки вращения, коллизии и другие вспомогательные элементы включаются по необходимости, а не показываются все сразу.

### Шаг 4. Выбрать возможности

Главный вопрос: **«Что должен уметь этот объект?»**

Пользователь выбирает карточки с обычными формулировками. Например:
- Можно подобрать.
- Можно открыть и закрыть.
- Хранит предметы.
- Можно экипировать.
- Наносит урон.
- Получает урон.
- Можно разрушить.
- Двигается.
- Следует за игроком.
- Можно использовать.
- Издаёт звуки.
- Создаёт другие объекты.
- Исчезает через заданное время.

Набор карточек расширяется подключаемыми пакетами. Поиск должен понимать задачу на обычном языке: пользователь может искать «поднять», «подобрать» или «забрать в инвентарь».

При выборе карточки показывается короткое объяснение и, когда полезно, маленькая схема результата. После подтверждения плагин устанавливает необходимые внутренние части и связи автоматически.

Если нужна дополнительная зависимость, плагин не добавляет её молча: он пишет, например, «Чтобы предмет можно было подобрать, нужно добавить область обнаружения. Добавить?» — и предлагает одну понятную кнопку.

### Шаг 5. Настроить поведение

Появляются только настройки выбранных возможностей.

Примеры:
- Урон: 10.
- Здоровье: 100.
- Скорость: 120.
- Дальность действия: 48.
- Вместимость: 20 предметов.
- Время открытия: 1 секунда.
- Автоматически закрывать: Да/Нет.
- Нужен ключ: Да/Нет.

Названия и единицы измерения должны быть понятны. Для сложной настройки рядом есть короткая подсказка и пример результата. Значения по умолчанию позволяют продолжить, даже если пользователь ничего не меняет.

### Шаг 6. Нажать «Попробовать»

Встроенный предпросмотр запускает временный экземпляр текущего объекта.

В нём можно проверить внешний вид, анимацию, коллизии, взаимодействие и выбранные возможности. Например, открыть сундук, подобрать предмет, нанести удар или запустить механизм.

Предпросмотр не меняет оригинал и не создаёт пользователю отдельные тестовые сцены. Кнопка «Сбросить» возвращает тестовый экземпляр к исходному состоянию.

### Шаг 7. Сохранить и использовать

Пользователь нажимает «Сохранить». Объект появляется в библиотеке.

Кнопка «Добавить в игру» или перетаскивание карточки в сцену создаёт экземпляр в игровом мире. Для обычной работы пользователь не обязан открывать исходную сцену объекта.

Изменения конкретного экземпляра — например, другое здоровье только у одного врага — не должны менять базовый объект в библиотеке.

## 6. Рабочая область: что именно находится на экране

### Верхняя панель

Только самые нужные действия:
- назад в библиотеку;
- имя объекта и статус сохранения;
- отмена и повтор;
- «Попробовать»;
- «Сохранить»;
- меню дополнительных действий;
- переключатель расширенных инструментов.

Не выводить одновременно все редкие команды.

### Центральная область

Большое визуальное поле с объектом. Оно занимает основное место экрана.

Пользователь может:
- перетаскивать изображение;
- выделять отдельные части;
- перемещать, вращать и масштабировать;
- менять положение элементов мышью;
- видеть результат без перехода в отдельный Inspector.

Вспомогательные контуры, сетка, pivot, точки крепления и коллизии доступны отдельными кнопками-переключателями.

### Боковая панель

Три понятные вкладки:

**Внешний вид** — изображения, части, анимации, размер, положение и визуальные эффекты.

**Возможности** — включённые возможности, добавление новых и их краткие описания.

**Настройки** — обычные параметры объекта, сгруппированные по смыслу.

Содержимое боковой панели зависит от выбранного элемента. Не показывать пустые секции и не повторять один и тот же параметр в нескольких местах.

### Нижняя панель

Не нужна постоянно. Появляется по запросу или при наличии важной ошибки. Содержит предпросмотр деталей, предупреждения и журнал технических событий. В простом режиме технические логи скрыты.

## 7. Каталог возможностей — сердце конструктора

Компоненты являются внутренней реализацией. Пользователь выбирает не компонент, а понятную возможность.

У каждой карточки возможности есть:
- понятное название;
- иконка;
- короткое описание;
- пример того, что она добавляет;
- базовые настройки;
- информация о необходимых других возможностях;
- кнопка добавления или удаления.

Примеры:
- «Можно подобрать» внутри использует механику подбора и связь с инвентарём.
- «Получает урон» может использовать Health и Damageable.
- «Можно разрушить» связывает здоровье, коллизии и событие разрушения.
- «Можно открыть» настраивает взаимодействие и состояния.
- «Двигается» подключает подходящий способ движения.

Плагин определяет совместимые узлы и устанавливает их сам. Внутренние привязки должны храниться явно и проверяться. Нельзя молча прикреплять компонент не туда, куда требуется.

Категории в каталоге — средство поиска, а не запреты. Пользователь может сочетать любые совместимые возможности.

## 8. Универсальность без отдельных конструкторов

Не делать специальные редакторы с разной логикой для каждого типа объекта. Использовать одинаковые инструменты внешнего вида, возможностей, настроек и предпросмотра.

Примеры стартовых рекомендаций:

| Что создаём | Возможности, которые можно предложить |
|---|---|
| Предмет | Можно подобрать, можно использовать, можно складывать в стопку |
| Ресурс | Получает урон, можно добыть, выдаёт предметы |
| Оружие | Наносит урон, можно экипировать, имеет прочность |
| Персонаж или NPC | Двигается, получает урон, взаимодействует, использует поведение |
| Снаряд | Двигается, наносит урон, исчезает через время |
| Контейнер | Открывается, хранит предметы, может быть заперт |
| Механизм | Взаимодействует, переключает состояния, запускает другие объекты |
| Постройка | Имеет коллизии, может взаимодействовать с миром |
| Эффект | Проигрывает анимацию, звук или частицы |

Это только подсказки. Любое сочетание возможностей должно оставаться доступным.

## 9. Ошибки должны помогать, а не пугать

Нельзя показывать новичку сообщения вроде «Invalid NodePath», «Missing Component Binding» или длинную трассировку GDScript как единственный способ понять проблему.

Примеры человеческих сообщений:
- «Не выбрано изображение. Добавь картинку или выбери её из проекта».
- «Для открытия нужна анимация. Создать простую анимацию автоматически?»
- «Эта возможность использует здоровье, но у объекта пока нет настройки здоровья. Добавить её?»
- «Часть объекта больше не найдена. Выбери её заново».

У ошибки должно быть действие: «Исправить», «Добавить», «Выбрать» или «Подробнее». Технические подробности доступны отдельно.

Предупреждения не должны блокировать сохранение, если они не влияют на работоспособность объекта. Перед удалением и массовыми изменениями показывать последствия.

## 10. Встроенный предпросмотр

Предпросмотр — обязательная часть простого пути.

Требования:
- запускать текущую версию черновика, а не последнюю сохранённую версию;
- не изменять исходное определение;
- очищать временное состояние при сбросе или закрытии;
- позволять вызвать основные события объекта;
- показывать коллизии и вспомогательные зоны по запросу;
- не создавать отдельные тестовые сцены в проекте;
- объяснять, что именно нельзя проверить в текущем preview, вместо имитации успешной проверки.

Для проверки runtime-логики разработчики проекта могут использовать автоматические smoke-тесты без демонстрационных сцен-манекенов.

## 11. Библиотека и работа с экземплярами

Карточка объекта показывает изображение, имя, категорию и понятные предупреждения. Поиск работает по названию, описанию, тегам и возможностям.

Пользователь может открыть, создать копию, превратить объект в шаблон, импортировать, экспортировать или удалить его.

Определение библиотеки является исходной версией. Экземпляр в игровой сцене может иметь собственные переопределения. Изменение одного экземпляра не должно менять другие экземпляры или оригинал.

Обновление сохранённого объекта не должно автоматически и неожиданно переписывать все размещённые экземпляры. Плагин показывает изменения и позволяет выбрать, какие экземпляры обновлять.

## 12. Внутренняя архитектура: сложность остаётся внутри

Внутреннее устройство должно быть достаточно мощным, чтобы поддерживать простой интерфейс, расширения и нестандартные игровые механики. Эти термины не являются обязательной частью интерфейса новичка.

### Слои системы

- **Object Builder Editor** — простой интерфейс, библиотека, визуальное поле, каталог возможностей, расширенный режим, Preview и диагностика.
- **Object System Runtime** — создание объектов, применение свойств и возможностей во время игры. Не зависит от интерфейса редактора.
- **Object Library** — определения, сцены, шаблоны, изображения и зависимости.
- **Extension Registry** — подключаемые возможности, профили, редакторы, валидаторы, типы свойств и действия.

### Модель объекта

Объект хранит:
- постоянную идентичность и метаданные;
- сцену с настоящими узлами Godot;
- пользовательские свойства;
- список выбранных возможностей;
- внутренние привязки возможностей к узлам;
- состояния и логику;
- ссылки на другие объекты и ресурсы;
- данные предпросмотра и версию схемы.

### Три уровня компонента

- **Component Type** — описание доступной внутренней реализации.
- **Component Binding** — связь конкретной возможности с конкретным узлом и настройками.
- **Runtime Instance** — работающий компонент внутри экземпляра игры.

Это разделение обязательно внутри архитектуры, но не должно показываться в простом режиме.

Привязка хранит стабильный ID, тип, ID целевого узла или NodePath, enabled, settings и версию. Старые определения, в которых компоненты были привязаны к корню, должны продолжать работать после безопасной миграции. Если явно указанный узел отсутствует, показывается ошибка; нельзя незаметно переносить компонент в другое место.

### Карточка возможности и автоматическая сборка

Карточка возможности связывает пользовательское описание с внутренней реализацией:
- название, картинка и понятное описание;
- необходимые узлы и компоненты;
- начальные свойства и настройки;
- автоматические связи;
- допустимые сочетания и конфликты;
- команды Preview;
- проверку корректности;
- подсказки и действия исправления.

При выборе возможности плагин строит план изменений, показывает его простым языком и применяет как одну Undo/Redo-операцию. Пользователь может увидеть созданные части в расширенном режиме.

### Профили

Профиль — необязательный набор хороших стартовых настроек. Он помогает начать, но не задаёт допустимые действия и не создаёт отдельную ветку кода для категории объекта. Профили обнаруживаются реестром расширений, а не хранятся в одном жёстко зашитом словаре.

### Пользовательские свойства

Каждое свойство имеет стабильный property_id. Отображаемое имя, описание, тип, диапазон, значение по умолчанию и условия показа хранятся отдельно. Компоненты ссылаются на ID, а не на подпись поля. Простая форма скрывает внутренние ID.

Начальные типы: Boolean, Integer, Float, String, Enum, Vector2, Vector3, Color, Texture2D, AudioStream, PackedScene, Resource, Array, Dictionary и ссылки на узлы в поддерживаемом контексте.

### Расширения

Сторонний пакет может зарегистрировать новую возможность, компонент, профиль, тип свойства, редактор, действие, событие или валидатор. Он должен предоставить простое описание для карточки, а не только технический класс.

Новое расширение не должно требовать переписывания центрального интерфейса Object Builder.

## 13. Совместимость с Godot

Object Builder не должен запирать пользователя внутри плагина.

- В основе остаются настоящие Godot-сцены, узлы и ресурсы.
- В расширенном режиме можно открыть исходную сцену и штатный Inspector.
- Редактирование стандартных свойств не дублируется вторым несовместимым инспектором.
- Созданные объекты работают в игре при выключенном editor-плагине.
- Внутренние данные сериализуются и версионируются.
- Неизвестные данные не удаляются при открытии или сохранении.
- Перед миграцией или массовым обновлением создаётся резервная копия.

Ориентир для главного экрана — официальная система Main Screen Plugin Godot. Для контекстных полей возможно применение EditorInspectorPlugin и EditorProperty.

## 14. Что реализовано сейчас и чего пока нет

**Текущая реализация Object Builder 0.5.3:**
- библиотека и поиск, мастер со стартовыми профилями и шаблоны;
- ObjectDefinition schema 4, метаданные, резервные копии и отдельное хранение сцен;
- пользовательские свойства String, Integer, Float, Boolean и Vector2;
- базовое дерево сцены и синхронизация со штатным Inspector;
- панели Sprite2D и AnimatedSprite2D в расширенном режиме;
- Health, Damageable, Attack и Destructible с API регистрации пользовательских компонентных определений;
- ObjectComponentBinding: компоненты можно привязывать к разным узлам одного объекта, старый root-level формат сохранён;
- Capability Definition / Selection / Catalog / Service и четыре карточки пользовательских возможностей;
- автоматическое добавление базовой зависимости Health для получения урона и разрушения;
- первые вкладки «Простой режим» и «Расширенный режим», поиск карточек и простые настройки;
- добавление изображения через создание Sprite2D и сохранение открытой сцены вместе с определением;
- все диалоги ограничиваются рабочей областью текущего монитора, длинные формы прокручиваются;
- `ObjectCreationProfileDefinition` / `ObjectCreationProfileRegistry`: 12 встроенных профилей, регистрация расширений и вариант «Без профиля»;
- планы изменения выбора возможностей с проверкой зависимостей и Undo/Redo.

**Это первая рабочая вертикаль, а не готовый простой конструктор.** Интерфейс пока остаётся dock; библиотека отображается списком; мастер использует компактный список профилей, а не иллюстрированные карточки; полноценного canvas, широкого каталога возможностей, центральной вкладки Godot и Preview нет.

## 15. Порядок разработки

Актуальная подробная дорожная карта находится в OBJECT_BUILDER_ROADMAP.md. Следующий приоритет после 0.5.2:
1. Стабилизировать Capability Definition, зависимости, конфликты, схемы настроек и транзакции Undo/Redo.
2. Вынести возможности, компоненты и профили в расширяемые реестры.
3. Перейти на центральную Main Screen Plugin-вкладку.
4. Перестроить библиотеку и мастер.
5. Создать полноценный визуальный canvas для частей объекта.
6. Расширить каталог механик и контекстные настройки.
7. Добавить безопасный Preview текущего черновика.
8. Добавить визуальные коллизии, sockets, состояния, события, Instance Overrides и Extension API.

Порядок выбран по пользовательской ценности. Не расширять каталог механик массово до стабилизации контракта Capability и транзакционной установки.

## 16. Критерии готовности

Object Builder соответствует своей главной идее, когда:

- новичок без знания Godot может создать простой объект и добавить его в сцену;
- для обычного объекта не требуется писать код или работать с деревом узлов;
- пользователь выбирает понятные возможности, а плагин сам готовит техническую реализацию;
- параметры показываются только тогда, когда они нужны;
- каждая сложная настройка имеет понятное объяснение;
- Preview проверяет черновик, а не отдельную вручную созданную тестовую сцену;
- один и тот же набор инструментов подходит для разных категорий объектов;
- продвинутый разработчик может открыть настоящую структуру и изменить её вручную;
- выключение плагина не ломает готовые игровые объекты;
- новые возможности можно подключать без переписывания центрального интерфейса.

### Приёмочные сценарии

Перед выпуском простого режима проверить как минимум несколько разных по природе объектов: подбираемый предмет, интерактивный механизм, оружие или снаряд, персонаж/NPC и составной объект. Это проверки универсальности одного конструктора, а не отдельные специальные редакторы. Проверки runtime выполнять автоматизированными smoke-тестами; не создавать демонстрационные .tscn-сцены только ради проверки простых вычислений или API.
