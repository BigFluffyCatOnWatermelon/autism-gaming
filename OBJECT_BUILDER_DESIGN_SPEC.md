# Object Builder — целевая универсальная архитектура

Статус: проектная спецификация. Godot 4.7.2, первый целевой формат — 2D.
Документ дополняет, но не заменяет авторские ROADMAP.md и OBJECT_BUILDER_SYSTEM_PLAN.md. Оригиналы остаются неизменными.

## 1. Главное решение

Object Builder — универсальная среда сборки игровых объектов, а не редактор деревьев, ресурсов, NPC или зданий. Любой объект создаётся из одной модели: структура сцены + визуальные и физические узлы + компонентные возможности + пользовательские свойства + состояния/события + связи + зависимости.

**Категория не ограничивает поведение. Профиль создания не является типом объекта.**

Разделяем:
1. Категория — расположение карточки в библиотеке; категории и подкатегории задаёт пользователь.
2. Профиль создания — необязательная стартовая конфигурация; предлагает root, свойства и компоненты, но ничего не запрещает.
3. Scene tree — реальная структура Godot-узлов.
4. Компоненты — подключаемые возможности; их можно назначать разным узлам, а не только корню.

«Дерево», «сундук», «меч», «животное», «снаряд» и «станок» — разные сочетания одной системы, не отдельные архитектурные ветки.

## 2. Модель объекта и слои данных

Объект — пакет связанных данных:

- **Object Definition:** постоянный ID, имя, категория, теги, описание, версия, пользовательские свойства, привязки компонентов, ссылки и зависимости.
- **Object Scene:** PackedScene с иерархией Godot-узлов, графикой, физикой, анимациями, аудио, маркерами и дочерними частями.
- **Component Bindings:** типы компонентов, целевые узлы и настройки.
- **Property Definitions:** типизированная схема пользовательских параметров.
- **Behavior Data:** состояния, события, условия и действия.
- **Object Links:** связи с другими объектами и точками крепления.
- **Preview Data:** миниатюра и настройки предпросмотра.
- **Dependencies:** текстуры, аудио, сцены, ресурсы, скрипты и другие объекты.

Definition — общий источник. Instance — размещённый в сцене или созданный runtime экземпляр. Instance Override меняет только выбранный экземпляр. Он не должен незаметно менять исходный Definition.

Разделять четыре вида данных: настройки редактора, определение библиотеки, временное preview-состояние и сохранённое игровое состояние.

### 2.1. Object Builder Editor
Папка addons/object_builder/. Отвечает за главную вкладку, библиотеку, мастер, редактор структуры, центральное 2D-поле, инспекторы, каталог компонентов, свойства, коллизии, sockets, события, preview, диагностику, импорт/экспорт, миграции и workspace. Плагин не содержит игровой логики. Отключение плагина не ломает созданные сцены.

### 2.2. Object System Runtime
Папка scripts/object_system/. Отвечает за загрузку определений и сцен, создание экземпляров, компоненты, свойства, события, состояния, связи, сохранение runtime-состояния и совместимость версий. Runtime не зависит от UI, EditorPlugin или редакторских singleton-объектов.

### 2.3. Object Library
Папка data/object_library/. Хранит определения, сцены, шаблоны, категории, коллекции, preview и индекс. Библиотека независима от конкретной игровой сцены и должна переноситься в другой проект.

### 2.4. Extension Registry
Реестр расширений: компонентов, профилей создания, типов свойств, редакторов полей, категорий, инструментов, валидаторов, событий и действий. Сторонний пакет добавляет возможность без изменения центрального скрипта плагина.

## 3. Главная навигация

Object Builder — отдельная главная вкладка Godot, не длинный вертикальный dock.

Четыре раздела:

**Библиотека:** все объекты, пользовательские категории, поиск, теги, фильтр компонентов, избранное, недавние, коллекции; сетка/список; карточки с миниатюрой, именем и предупреждениями; создать, открыть, дублировать, переместить, экспортировать и безопасно удалить.

**Редактор:** основная рабочая область, см. раздел 4.

**Шаблоны:** встроенные и пользовательские шаблоны, производные объекты и варианты. Шаблон — источник для создания копии/наследования, а не runtime-класс.

**Диагностика:** ошибки структуры, отсутствующие ресурсы, зависимости, несовместимые версии, повторные ID, неверные NodePath, проблемы миграции/импорта. Каждая запись кликабельна и открывает проблемное место.

Настройки плагина — меню через шестерёнку, а не постоянная вкладка.

## 4. Рабочее пространство редактора

Панели меняют размеры, скрываются и сохраняют раскладку. Сложность раскрывается постепенно.

### Верхняя панель
Имя объекта, статус сохранения, переключение документов, Undo/Redo, Save, Save As, Duplicate, Create Template, Validate, Preview, Add to Scene, Open Source Scene, командная палитра и дополнительные действия. Не показывать все команды сразу, а фильтровать по контексту.

### Левая зона — структура
Два режима:
- **Дерево сцены:** фактическая иерархия Godot, поиск, добавление, удаление, дублирование, переименование и перемещение. Значки показывают тип, компоненты, коллизии, анимацию и ошибки. Все операции через Undo/Redo.
- **Компоненты выбранного узла:** привязки, включение/отключение, настройка, перенос на другой узел, дублирование и удаление. Компоненты — отдельные привязки в модели данных, не обязательно дочерние узлы сцены.

### Центральная зона — 2D-поле
Режимы: обычный вид, структура/каркас, коллизии, hitbox/hurtbox, sockets, pivot/origin, служебные области и эффекты.
Инструменты: выбор, перемещение, поворот, масштаб, привязка к сетке, направляющие, zoom/pan, центрирование, изоляция узла, временное скрытие, контекстное меню.
Поле работает с обычными Godot-ресурсами и SceneTree. Сначала preview, выбор узла и базовые манипуляции с Undo/Redo; не переписывать сразу весь 2D-редактор Godot.

### Правая зона — контекстный инспектор
- Объект: ID, имя, категория, теги, иконка, описание, версия, зависимости.
- Узел: основные transform/visual поля и переход в штатный Inspector.
- Компонент: настройки только выбранного компонента.
- Свойства: определения и значения.
- Связи: object links и sockets.

Не создавать два независимых редактора одного поля. Стандартные свойства узлов редактируются штатным Inspector Godot. Object Builder добавляет формы для своих Definition, компонентов и специальных редакторов. Выбор узла синхронизируется со Scene dock/Inspector.

### Нижняя зона
По умолчанию свёрнута: ошибки, ресурсы/зависимости, события, журнал и результаты preview.

## 5. Универсальный мастер создания

Способы: пустой объект; встроенный/пользовательский шаблон; дубликат; импорт существующей Godot-сцены; импорт пакета. Все варианты создают один формат Definition + Scene.

Затем необязательный профиль: общий объект, ресурс, предмет, оружие, персонаж, NPC, животное, снаряд, контейнер, механизм, постройка, эффект или пользовательский профиль. Можно выбрать «Без профиля». Профиль только предлагает root, свойства, компоненты и структуру; всё изменяемо.

Мастер задаёт имя, ID, категорию, теги, описание, иконку и root-тип Godot из доступных поддерживаемых типов. Создаётся черновик Definition и Scene, сразу открывается редактор. Изменение root позже — отдельная безопасная операция с предупреждением о несовместимых дочерних узлах.

Профили — ресурсы/пакеты, обнаруживаемые реестром. Не поддерживать их статическим словарём в plugin.gd.

## 6. Компоненты: тип, привязка, runtime instance

Разделить:
- Component Type — описание типа (Health, Audio и т. п.).
- Component Binding — привязка типа к узлу объекта.
- Component Instance — runtime-экземпляр во время игры.

Привязка содержит: binding_id, component_type_id, целевой NodePath или стабильный ID узла, enabled, settings, component_version, источник/пакет; execution order — только когда он нужен.

Текущая ObjectFactory создаёт все компоненты на корне. Целевая модель поддерживает любой target: Audio на аудио-узле, Hitbox на Area2D, Health на нужном узле. Отсутствующий target даёт диагностику, а не молчаливую привязку к корню.

Описание типа компонента содержит ID, имя, категорию, иконку, описание, версию/API, runtime script/class, схему настроек, группы сложности, обязательные/несовместимые компоненты, поддерживаемые узлы, события/действия, справку, миграции и опциональный редактор.

Каталог умеет искать, фильтровать, показывать совместимость и зависимости, подключать сторонние пакеты. Обязательные зависимости показываются явно; добавление не создаёт незаметно десятки других систем.

Категории — только фильтры. Начальный список:
- Внешний вид: Sprite, Animation, Visual Effects.
- Физика: Collision, Hitbox, Hurtbox, Physics, Movement, Pushable.
- Характеристики: Health, Defense, Resistance, Regeneration, Durability.
- Бой: Attack, Weapon, Projectile, Targeting.
- Разрушение/добыча: Destructible, Harvestable, Drop Table.
- Взаимодействие: Interactable, Pickup, Container, Lock, Trigger.
- Предметы/производство: Inventory, Equipment, Crafting, Recipe, Consumable.
- Звук: Audio, Audio Events.
- Поведение: State Machine, Patrol, Follow, Flee, AI, Navigation.
- Генерация: Procedural Generator, Random Variant.
- Связи: Attachment, Child Object, Spawn Link.
- Пользовательские компоненты.

Мир обращается к возможностям объекта, не к имени вроде oak_tree или rock_large. Категория «Природа» не означает возможность рубки.

## 7. Пользовательские свойства

Типы поэтапно: Boolean, Integer, Float, String, Enum, Vector2, Vector3, Color, Texture2D, AudioStream, PackedScene, Resource, Array, Dictionary, NodePath/ссылка на узел в поддерживаемом контексте.

Каждое поле имеет постоянный property_id, имя, описание, тип, default, группу, уровень сложности, min/max/step, Enum options, editability, visibility condition, правила сериализации и включение в шаблон. Компоненты ссылаются на property_id; переименование подписи не ломает ссылку. Схема и runtime-значение экземпляра разделены.

## 8. Визуальные, физические и structural редакторы

**Внешний вид:** Sprite2D, AnimatedSprite2D и CanvasItem; texture/region/frames; transform/Z; flip; несколько частей; AnimationPlayer/AnimationTree/SpriteFrames; autoplay, Loop Mode, скорость и направления.

**Физика:** несколько CollisionShape2D/CollisionPolygon2D; прямоугольник, круг, капсула, полигон; редактирование формы в 2D-поле; отдельные hitbox/hurtbox; Layer/Mask, масса, трение, упругость, гравитация. Объект не ограничивается одной коллизией.

**Origin и sockets:** именованные точки с ID и назначением: Pivot, HitPoint, DropPoint, FallPivot, FruitPoint и пользовательские. Положение/поворот редактируются визуально; другие части/объекты ссылаются по ID.

## 9. Состояния и события

Состояния меняют текстуры, анимации, коллизии, действия, свойства, звуки, частицы и видимость. Примеры: Closed/Open, Intact/Damaged/Destroyed, Active/Inactive.

Визуальная логика: событие → условие → действие → следующее событие. Пример: On Interact → Check Key → Change State → Play Animation → Play Sound. Для уникальных сценариев остаётся пользовательский GDScript.

## 10. Встроенный Preview

Preview — режим внутри редактора, не отдельные ручные сцены-манекены. Возможности: статичный вид, анимации, состояния, коллизии, sockets, звуки, частицы, взаимодействия, урон, разрушение, дроп и тестовые значения.

Preview создаёт временный экземпляр из текущего черновика. Он не меняет Definition, World или игровые сохранения; его можно сбросить.

## 11. Библиотека и хранение

Целевое направление:
- addons/object_builder/ — редактор.
- scripts/object_system/ — runtime.
- data/object_library/objects/ — определения и сцены.
- data/object_library/templates/ — шаблоны.
- data/object_library/categories/ — пользовательские категории.
- data/object_library/collections/ — коллекции.
- data/object_library/previews/ — миниатюры.
- data/object_library/library_index.tres — восстанавливаемый индекс.

Карточка хранит ID, имя, категорию, подкатегорию, иконку, preview, описание, теги, сцену, версии, компоненты и зависимости. Категория — метаданные, не обязательный путь файла.

Библиотека не смешивается с Cozy Village/asset packs. Импорт/экспорт переносит зависимости, проверяет ID-конфликты и missing resources, показывает diff, создаёт backup и отчёт.

## 12. Definition, Scene, Template, Variant, Instance

Definition — исходный объект; Scene — структура Godot; Template — источник новой копии; Variant — производная конфигурация; Instance — объект в сцене/runtime; Instance Override — локальное значение.

Instance хранит source object ID и базовую версию. Обновление Definition не переписывает все сцены автоматически. Пользователь выбирает экземпляры, видит diff, разрешает конфликты и может отвязать экземпляр. Неизвестные пользовательские поля не удаляются.

## 13. Диагностика и безопасность

Красные ошибки: пустой/повторный ID, отсутствующий root/scene, потерянная обязательная ссылка, неизвестный обязательный компонент, несовместимая версия, отсутствующий target node.

Жёлтые предупреждения: нет иконки/preview, необязательной коллизии, неиспользуемый ресурс, рекомендуемая зависимость.

Каждая запись ведёт к узлу/полю и предлагает действие. Все изменения поддерживают Undo/Redo. Перед массовой операцией и миграцией создаётся backup. Неизвестные поля сохраняются.

## 14. Что есть сейчас и что требуется изменить

**Уже реализовано:** ObjectDefinition и версии; базовые PropertyDefinition; ObjectComponentDefinition; ObjectFactory/Registry; библиотека/шаблоны; поиск, теги, избранное, недавние; мастер с кодовыми профилями; дерево сцены и синхронизация со штатным Inspector; базовые панели Sprite2D/AnimatedSprite2D; Health, Damageable, Attack, Destructible.

**Ограничения текущей реализации:**
- Сейчас это dock, не главная вкладка.
- Профили создания зашиты в plugin.gd.
- Каталог компонентов статический.
- Все компоненты создаются на корне; target NodePath не поддержан.
- Ограниченный набор типов пользовательских свойств.
- Нет полноценного редактируемого центрального 2D-поля.
- Нет редакторов коллизий и sockets.
- Нет состояний/событий.
- Нет встроенного Preview разных состояний/механик.
- Нет instance overrides/выборочного обновления.
- Нет полного импорта/экспорта зависимостей.

Похожие классы/названия не означают, что функция уже завершена.

## 15. Порядок реализации

Работать по универсальным возможностям, не по одному объекту:

1. Разделить Component Type, Binding и Runtime Instance; добавить target NodePath, совместимый fallback для старых root-level компонентов.
2. Создать расширяемые реестры компонентов и профилей.
3. Перестроить мастер: способ → необязательный профиль → metadata → root → draft.
4. Создать рабочую область: навигация, структура, контекстный инспектор, нижняя панель, сохранённые workspace.
5. Расширить визуальные/физические редакторы: 2D-поле, коллизии, sockets.
6. Расширить свойства и связи property ID с компонентами.
7. Добавить типизированные события и состояния, затем visual editor.
8. Создать встроенный Preview на временном экземпляре.
9. Добавить instance overrides, выборочное обновление и отвязку.
10. Реализовать диагностику библиотеки, import/export, миграции и backups.
11. Открыть API сторонним компонентам, профилям, свойствам, редакторам и валидаторам.

Новая возможность универсальна, только если не требует ветки кода для «дерева», «сундука» или другого имени.

## 16. Критерии готовности

Без изменения центрального кода пользователь может: создать пустой объект, использовать шаблон или импортировать сцену; создавать категории; собирать узлы; настраивать несколько визуальных/физических частей; делать коллизии и sockets; подключать компонент к любому узлу; создавать свойства и использовать их в компонентах; настраивать состояния/события; проверять во встроенном Preview; сохранять/повторно использовать; создавать Instance Overrides; безопасно обновлять экземпляры; экспортировать объект с зависимостями; использовать созданные объекты с отключённым плагином.

Перед 1.0 проверяются разные сценарии: интерактивный объект, персонаж с поведением, снаряд, подбираемый предмет и составной объект. Это проверки одной архитектуры, не отдельные подсистемы.
