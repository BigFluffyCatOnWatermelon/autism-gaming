# Object Builder — ускоренный процесс разработки

**Принцип:** меньше повторного кода, меньше повторного чтения и переписывания документов, меньше крупных рискованных изменений. Каждый шаг должен давать проверяемый результат.

## 1. Один источник истины для каждого типа информации

| Что нужно узнать | Где смотреть | Что не дублировать |
|---|---|---|
| Что делаем следующим | `TASKS.md` | Не переписывать список задач в README и Project State |
| Куда движется продукт | `OBJECT_BUILDER_ROADMAP.md` | Не хранить вторую дорожную карту |
| Как выглядит и работает UI | `OBJECT_BUILDER_UI_SPEC.md` | Не описывать те же кнопки в архитектуре |
| Как проходит путь пользователя | `OBJECT_BUILDER_WORKFLOW.md` | Не использовать сценарий как список реализации |
| Как устроены данные и runtime | `ARCHITECTURE.md` | Не копировать реализацию из README |
| Что уже есть сейчас | `PROJECT_STATE.md` | Держать это кратким снимком, а не историей |
| Что изменилось | `CHANGELOG.md` | Не копировать туда задачи и будущие планы |
| Как запустить и пользоваться | `README.md` | Только актуальные инструкции |

Документы обновляются по факту изменения соответствующей информации. Для каждой задачи не нужно одновременно переписывать Roadmap, UI Spec, Workflow, Architecture, README и Project State.

## 2. Маленькие вертикальные срезы

Предпочтительный размер одной задачи:
- один пользовательский сценарий;
- один экран/панель или одна законченная операция;
- ограниченный набор связанных файлов;
- один понятный commit.

Порядок работы:
1. Посмотреть текущую реализацию и повторно используемые сервисы.
2. Выбрать самый короткий путь к целевому результату.
3. Реализовать законченную часть, а не заготовить 5 пустых подсистем.
4. Добавить smoke/regression проверку.
5. Проверить импорт/разбор и запуск основной сцены.
6. Обновить только затронутую документацию и коммитить.

Не разбивать логически цельную задачу на множество мелких веток и не создавать отдельную архитектуру, если текущий сервис уже решает задачу.

## 3. Переиспользуемые UI-шаблоны

Общий набор находится в `addons/object_builder/ui/ui_factory.gd`.

| Шаблон | Для чего использовать |
|---|---|
| `add_labeled_control` | Подпись + поле ввода/переключатель |
| `add_labeled_line_edit` | Однострочное текстовое поле с подписью |
| `create_section_title` | Единообразные заголовки разделов |
| `add_empty_state` | Пустая библиотека/список с переносом текста |
| `add_action_button` | Кнопка с tooltip и заранее подключённым действием |
| `make_spin_box` | Числовой ввод с min/max/step |
| `create_scrollable_dialog_body` | Ограниченная форма диалога с внутренней прокруткой |
| `popup_window_safely` | Единое ограничение popup по рабочей области монитора |
| `clear_children` | Очистка динамического списка без копирования цикла |

**Правило:** сначала использовать готовый helper. Если встречается несколько одинаковых реализаций, вынести общее правило в factory и проверить его один раз. Не обобщать элементы с разным смыслом только ради уменьшения числа строк.

## 4. Архитектурное разделение

- `plugin.gd` — lifecycle EditorPlugin, состояние документа и маршрутизация действий.
- `ui/ui_factory.gd` — общие визуальные примитивы и правила поведения контролов.
- `scripts/object_system` — модель объектов, каталоги, фабрика, валидация и сохранение.
- Следующий безопасный этап декомпозиции — вынос самостоятельных экранов (Library View, Object Editor View, Dialogs) в отдельные контролы с собственным состоянием и сигналами. Делать это по одному экрану и не переносить бизнес-логику в UI.

## 5. Оптимизация проверок

В GitHub Actions один общий workflow выполняет:
1. Импорт и загрузку editor plugins через Godot 4.7.2.
2. Object System smoke tests.
3. UI factory smoke tests.
4. Существующие regression smoke тесты модулей — они остаются обязательными, даже пока новые механики не разрабатываются.
5. Headless запуск основной сцены.

Новые механики не добавлять. Текущие тесты пакетной системы запускать как регрессионные проверки; они защищают существующее поведение.

## 6. Что пока не делать

- Не создавать отдельную ветку для каждого небольшого изменения: основная рабочая ветка — `main`.
- Не переписывать весь `plugin.gd` одним заходом.
- Не делать массовую миграцию старых сцен.
- Не добавлять новые механики и не переводить Planned в Implemented.
- Не создавать второй UI framework поверх Godot Containers.
- Не писать одну и ту же инструкцию в нескольких документах.
- Не добавлять helper, который используется только один раз и не стандартизирует важное поведение.

## 7. Definition of Done

- [ ] Пользовательский результат соответствует задаче.
- [ ] Повторно использованы существующие сервисы, шаблоны и UI factory.
- [ ] Не дублируется логика в UI и runtime.
- [ ] Проверены сохранение и обратная совместимость, если менялись данные.
- [ ] Прошли целевые smoke/regression тесты.
- [ ] Проект импортируется, скрипты разбираются, основная сцена запускается.
- [ ] Changelog обновлён; остальные документы — только при реальном изменении их содержания.
- [ ] Изменения находятся в `main`; GUI-неопределённости прямо перечислены.
