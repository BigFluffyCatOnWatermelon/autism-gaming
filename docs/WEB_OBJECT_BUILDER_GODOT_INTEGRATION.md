# Web Object Builder — интеграция с Godot

**Статус документа:** рабочая документация начального переноса  
**Версия интеграции:** 0.1.0-dev  
**Целевая версия проекта:** Godot 4.7.2  
**Рабочая ветка:** `feature/web-object-builder-godot-integration`

## 1. Цель

Перенести существующую веб-версию Object Builder внутрь редактора Godot, сохранив HTML/CSS/JavaScript интерфейс и его самостоятельную работоспособность.

На этом этапе веб-редактор и нативный Object Builder **не объединяются**. Они существуют параллельно. Это сознательная граница: сначала проверяем размещение веб-интерфейса в редакторе, а уже затем подключаем его к нативной модели.

## 2. Источник веб-версии

Исходная версия взята из ветки `feature/mechanic-addition-web-test`:

- `docs/object-builder/index.html`
- `docs/object-builder/app.css`
- `docs/object-builder/app.js`

Копия для Godot расположена в:

```text
addons/web_object_builder/
├── plugin.cfg
├── plugin.gd
├── README.md
└── web/
    ├── index.html
    ├── app.css
    ├── app.js
    └── host_bridge.js
```

Исходный каталог `docs/object-builder/` не удаляется и не заменяется. Его можно продолжать использовать как самостоятельную веб-версию.

## 3. Встраивание

Для первой реализации выбран Godot WRY. В интеграционной ветке его GDExtension уже находится в `addons/godot_wry/` (в том числе Windows x86_64 DLL), поэтому отдельно копировать WRY не нужно:

- Windows: системный WebView2 (Chromium).
- macOS: WebKit.
- Linux: WebKitGTK под X11.

WRY предпочтительнее CEF для этого проекта, потому что использует системный WebView вместо поставки полного браузерного runtime в репозитории. Для Windows требуется WebView2 Runtime. На Windows 11 он входит в систему; на части устройств Windows 10 его также может не быть.

Полезные ссылки:

- [Godot WRY — исходный репозиторий](https://github.com/doceazedo/godot_wry)
- [Godot WRY — установка](https://godot-wry.doce.sh/guide/getting-started.html)
- [Godot WRY — API WebView](https://godot-wry.doce.sh/reference/webview.html)
- [Microsoft — WebView2 Runtime](https://developer.microsoft.com/microsoft-edge/webview2/)

### Почему не CEF

CEF обеспечивает собственный Chromium, но требует существенно большего объёма поставки и настройки. Кроме того, ранее рассматривавшийся gdCEF был архивирован upstream 5 ноября 2026 года. Поэтому для первого интеграционного слоя выбран более лёгкий системный WebView2 через WRY. При необходимости браузерный backend можно будет заменить, сохранив контракт Web Object Builder.

## 4. Плагин редактора

Плагин `addons/web_object_builder/plugin.gd`:

1. Регистрирует отдельную центральную вкладку `Web Object Builder`.
2. Проверяет наличие класса `WebView`, предоставляемого Godot WRY.
3. Создаёт WebView на всю область центральной вкладки.
4. Загружает локальную страницу `res://addons/web_object_builder/web/index.html`.
5. Выделяет постоянный каталог профиля браузера в `user://web_object_builder/webview`.
6. Подключает IPC-сигнал для будущих сообщений от JavaScript.
7. При отсутствии WRY показывает понятную инструкцию вместо ошибки загрузки плагина.

WebView всегда рисуется поверх остальных элементов Godot UI. Поэтому на первом этапе он размещается в отдельной центральной вкладке, а не встраивается в панели Inspector или SceneTree.

## 5. Установка и запуск

1. Обнови рабочую копию до ветки `feature/web-object-builder-godot-integration`.
2. Открой проект в Godot 4.7.2 и дождись импорта файлов.
3. Полностью перезапусти редактор, чтобы GDExtension зарегистрировал класс `WebView`.
4. Открой Project → Project Settings → Plugins и включи `Web Object Builder`.
5. Открой центральную вкладку `Web Object Builder`.

Плагин проверяет наличие `WebView`, а при необходимости явно вызывает `GDExtensionManager.load_extension()` для `addons/godot_wry/WRY.gdextension`. Если регистрация не удалась, вкладка показывает диагностическую панель, а Output содержит код результата загрузки.

На Windows отдельно проверь наличие [WebView2 Runtime](https://developer.microsoft.com/microsoft-edge/webview2/). Microsoft указывает, что Runtime включён в Windows 11, но на некоторых устройствах Windows 10 может отсутствовать.

## 6. Хранение на первом этапе

Веб-приложение пока оставляет собственную модель и использует `localStorage`. Существующие ключи приложения, включая `ob-v2-project`, `ob-v2-library` и `ob-v2-library-categories`, не мигрируют автоматически.

Профиль WRY хранится в `user://web_object_builder/webview`, что позволяет сохранять browser storage между перезапусками редактора.

Это временный этап. После объединения данные веб-конструктора будут преобразовываться и сохраняться через нативные ресурсы Godot. До появления проверенной миграции нельзя удалять или очищать browser storage.

## 7. Мост JavaScript ↔ GDScript

Файл `web/host_bridge.js` добавляет необязательный интерфейс:

```javascript
ObjectBuilderHost.isEmbedded
ObjectBuilderHost.send("object_selected", { objectId: "tree_oak" })
ObjectBuilderHost.on("scene_updated", (payload) => { /* ... */ })
```

Godot принимает сообщения через сигнал `web_message_received` и может отправить сообщение методом `send_to_web(type, payload)`.

Обёртка проверяет наличие `window.ipc`. Если приложение открыто в обычном браузере, хост считается недоступным, но веб-конструктор продолжает работать. Это сохраняет возможность параллельного использования web-версии.

На этом этапе транспортный канал является только инфраструктурой: команды предметной области ещё не подключены.

## 9. Правила безопасности данных

- На первом этапе нативная библиотека не изменяется веб-приложением.
- Не удалять связанные объекты без явной политики связей и проверки входящих ссылок.
- При IPC принимать только сообщения ожидаемого канала, проверять тип и размер данных.
- Не выполнять произвольный JavaScript, пришедший из JSON или пользовательских данных.
- Все операции записи на этапе объединения должны иметь валидацию и атомарный откат.
- Изменения модели должны проходить через единый сервис, а не напрямую из UI.

## 10. Проверка и известные ограничения

**Важно:** исходники перенесены и статически просмотрены, но запуск Godot и WRY в этой среде не выполнялся. Нельзя считать реальное отображение страницы, фокус ввода и поведение окон подтверждёнными до ручной проверки в Godot 4.7.2.

Веб-приложение пока сохраняет данные в браузерном хранилище. Оно не создаёт настоящие сцены Godot. Слой IPC пока не управляет нативными объектами.

Известная особенность WRY: WebView отображается поверх других Godot UI элементов. Это ограничивает свободное смешивание HTML-панелей с нативными Inspector/SceneTree контролами; для отдельной центральной вкладки это приемлемо.

## 12. Устранение неполадок вкладки

Если нажатие на вкладку не показывает интерфейс:

1. Убедись, что в Plugins включён именно **Web Object Builder**.
2. Проверь, что Godot WRY 1.0.2+ распакован в `res://addons/`, а его файл `.gdextension` и каталог `bin/` находятся на месте.
3. Полностью перезапусти редактор после установки WRY: расширения GDExtension регистрируют класс `WebView` при старте Godot.
4. Открой панель Output и найди сообщения с префиксом `Web Object Builder:`.
   - `editor screen registered. WebView available: false` — WRY не зарегистрировал класс `WebView`.
   - `loading res://...` без `page load finished` — WebView создан, но страница не завершила загрузку; включён DevTools, его можно открыть правым кликом внутри страницы.
   - `page load finished` — движок сообщил об окончании загрузки, проверь видимость и ввод.
5. При отсутствии WRY сама вкладка должна показать диагностическую панель с кнопками установки и открытия исходной веб-версии отдельно.
6. В Windows проверь Microsoft Edge WebView2 Runtime.

Плагин добавляет корневую панель в дерево редактора до создания содержимого. При переключении центральной вкладки отдельно переключает видимость нативного WebView через его `set_visible()`, а не только видимость Godot Control. Это необходимо, потому что WRY отображает webview как нативный UI элемент ОС поверх содержимого Godot.

Если страница не грузится, проверь версию WRY. Поддержка `res://` в `load_url()` добавлена в WRY v1.0.2; старые сборки могут не загружать локальную точку входа.


## 13. Исправления после первого запуска

В обновлении от 9 ноября 2026:
- Корневая панель теперь сначала добавляется в `EditorInterface.get_editor_main_screen()`, и только после этого создаются WebView или диагностические контейнеры. Это гарантирует, что контейнеры получают активный viewport и могут рассчитать размеры.
- При переключении вкладки вызывается нативный метод WRY `set_visible()`, дополнительно к изменению видимости родительского Control.
- Добавлено логирование `_make_visible()`, регистрации WebView, начала загрузки и завершения загрузки.
- Включён DevTools для диагностики ошибок HTML/JS.
- Добавлена кнопка открытия локальной веб-версии отдельно, когда WRY отсутствует.
- Для хранения профиля учитывается свойство WRY 1.0.2 `user_data_directory`; старое имя свойства задаётся только если оно присутствует в установленной сборке.

Если в Output есть сообщение `WebView available: false`, сама интеграция работает, но GDExtension WRY не загрузилась. Если есть `page load started`, но нет `page load finished`, проверяй адрес и DevTools. Если оба сообщения есть, но окно пустое, нужно исследовать позиционирование/видимость native WebView на конкретной системе.

**Проверка на реальном редакторе всё ещё обязательна:** текущая среда не содержит установленный Godot 4.7.2 и бинарники WRY, поэтому подтверждение отображения, фокуса и ввода выполнить здесь нельзя.


## 14. Встроенная зависимость Godot WRY

Ветка содержит Godot WRY в `addons/godot_wry/`. Для Windows x86_64 предусмотрена библиотека `bin/x86_64-pc-windows-msvc/godot_wry.dll`. Плагин Web Object Builder сначала проверяет регистрацию `WebView`; если класс отсутствует, выполняет явную загрузку файла `WRY.gdextension` через `GDExtensionManager`.

Если загрузка не удалась, проверь:
- Output → сообщение `WRY load status = N`;
- ошибки загрузки DLL и её зависимостей;
- разрядность Godot (поставляется Windows x86_64);
- наличие WebView2 Runtime.

Не скачивай и не распаковывай поверх `addons/godot_wry/` другой релиз без необходимости: сначала проверь статус загрузки встроенной сборки.


## 15. Исправление начальной загрузки WebView

Логи первого запуска показали, что GDExtension зарегистрировала класс `WebView`, но переход страницы не вызывал сигналы `page_load_started` / `page_load_finished`. Это указывало на участок первичной навигации.

Исправление:
- Перед добавлением узла в дерево сцены адрес теперь задаётся через экспортируемое свойство `url`.
- Это соответствует официальному примеру WRY, где `url` задаёт начальную страницу узла.
- `load_url()` оставлен только как совместимый fallback для сборок, где свойство `url` недоступно.
- В Output теперь различаются сообщения `initial URL property configured` и `loading URL through load_url()`.

Официальная документация WRY описывает `url` как начальный URL и `load_url()` как метод последующей навигации: [WebView API](https://godot-wry.doce.sh/reference/webview.html). После обновления ветки ожидаемое сообщение в Output:

```text
Web Object Builder: initial URL property configured: res://addons/web_object_builder/web/index.html
Web Object Builder: page load started: ...
Web Object Builder: page load finished: ...
```

Если начальная загрузка всё ещё не запускается, следующий шаг — сравнить поведение того же WebView с минимальной встроенной тестовой страницей WRY (`addons/godot_wry/examples/test.html`). Это отделит проблему браузерного backend от загрузки ресурсов самого Object Builder.


## 16. Исправление серого WebView в редакторе Godot

Повторные логи пользователя показали:
- класс \`WebView\` зарегистрирован;
- плагин создаёт узел и задаёт начальный URL;
- события \`page_load_started\` и \`page_load_finished\` отсутствуют;
- экран остаётся серым.

Причина найдена в исходном коде используемой GDExtension Godot WRY. Класс объявлен как \`#[class(base=Control)]\`, а нативная поверхность создаётся в callback \`ready()\`, который вызывает метод \`create_webview()\`. Класс не помечен как \`tool\`, поэтому при создании из EditorPlugin callback инициализации не выполняется в редакторе. Метод \`create_webview()\` экспортирован в Godot и может быть вызван вручную.

Исправление:
1. WebView создаётся только при первом открытии вкладки, когда центральная область уже видима.
2. В свойствах узла очищается начальный URL по умолчанию, указывается диагностический HTML.
3. После добавления узла в дерево редактора плагин явно вызывает \`create_webview()\`.
4. После кадра редактора вызывается \`resize()\`, чтобы пересчитать реальные границы нативной поверхности.
5. Диагностическая HTML-страница отправляет IPC-сообщение \`webview_bootstrap_ready\`. После его получения GDScript загружает основной \`res://addons/web_object_builder/web/index.html\`.
6. В самой диагностической странице оставлена кнопка «Открыть Object Builder» на случай, если HTML отображается, но автоматическое IPC-сообщение не пришло.

Это отделяет три уровня проверки:
- **Нативная поверхность:** создан ли WebView и виден ли он.
- **HTML/IPC:** отображается ли inline HTML и работает ли канал сообщений.
- **Локальный фронтенд:** загружается ли реальный Object Builder через \`res://\`.

Важные исходники/обсуждения:
- [Реализация WebView в WRY](https://github.com/doceazedo/godot_wry/blob/b1783bbd610a630b2f315dd66251f8b7a5ced445/rust/src/lib.rs) — \`ready()\` вызывает \`create_webview()\`; последний строит нативную поверхность и подключает resize/visibility.
- [WRY issue #4 — Running webview in the editor (@tool)](https://github.com/doceazedo/godot_wry/issues/4).
- [WRY issue #52 — Running in the editor as a plugin](https://github.com/doceazedo/godot_wry/issues/52).

После обновления ожидаемый Output:
\`\`\`text
Web Object Builder: create_webview() called explicitly for editor mode.
Web Object Builder: native WebView initialized. Rect = ...
Web Object Builder: IPC received: webview_bootstrap_ready
Web Object Builder: navigating to Object Builder page: res://addons/web_object_builder/web/index.html
Web Object Builder: page load started: ...
Web Object Builder: page load finished: ...
\`\`\`

Если вместо интерфейса появляется диагностическая страница «WebView работает», но основной конструктор не загружается, значит нативный WebView и IPC уже исправны; тогда надо отдельно исследовать custom protocol \`res://\` или загрузку HTML/CSS/JS.


## 17. Исправление нулевой высоты WebView

После ручного вызова `create_webview()` WRY может пересчитать нативную поверхность в момент переключения вкладок редактора и получить высоту Control равную нулю. Поэтому плагин больше не полагается только на `PRESET_FULL_RECT`: он фиксирует верхний левый якорь, задаёт фактический размер из контейнера редактора и синхронизирует границы при изменении размера. В Output должны появляться строки `WebView bounds synchronized` с ненулевыми шириной и высотой. Это исправление проверено статически; фактический рендеринг необходимо подтвердить в редакторе Godot.


## 18. Единая модель данных и нативный backend

В интегрированном режиме веб-редактор больше не является независимым прототипом с собственными объектами и localStorage. Единственный источник истины — нативные ресурсы ObjectDefinition и сервисы ObjectLibraryService, ObjectBuilderObjectCreationService, ObjectBuilderSceneDraftService, ObjectBuilderLibraryActionsService, ObjectCapabilityCatalog, ObjectCapabilityService, ObjectComponentCatalog и ObjectCreationProfileRegistry.

Новый слой addons/web_object_builder/services/object_builder_backend.gd принимает команды через IPC и переводит их в операции над этими ресурсами. Формат parts / caps / mechanicSettings / properties / relations в JavaScript — только DTO для отображения и обмена; при синхронизации он преобразуется в ObjectNodeDefinition, ObjectCapabilitySelection, ObjectPropertyDefinition, ObjectComponentDefinition и поля ObjectDefinition.

Веб-оболочка сохраняет идеи интерфейса прототипа:
- рабочая область с деревом частей, диаграммой структуры, свойствами, механиками и связями;
- настройки прямо в карточках подключённых механик, с нативной проверкой зависимостей и конфликтов;
- отдельная вкладка компонентов для расширенного ручного редактирования;
- каталог механик и профили создания, загружаемые из нативных реестров, а не статических массивов;
- отдельный список шаблонов, библиотека объектов, категории/подкатегории, избранное, недавние записи и коллекции;
- реальные вкладки открытых черновиков с независимым состоянием.

Все постоянные изменения проходят через нативные сервисы. Удаление объекта использует LibraryActionsService; связи — не владеющие ссылками на другие записи. Закрытие несохранённой вкладки удаляет только временную сцену этого черновика, если она не используется сохранённой записью. При сохранении, удалении и изменении файлов выполняется сканирование EditorFileSystem, а нативная вкладка Object Builder обновляет библиотеку по сигналу filesystem_changed.

Импорт сцены открывает нативный FileDialog и использует ObjectBuilderSceneDraftService.import_scene(). Открытие сохранённой сцены вызывает EditorInterface.open_scene_from_path(). Центральный canvas теперь показывает интерактивное дерево нативных узлов ObjectDefinition; он не заявляет, что является live-рендером игровой сцены. Для фактической сцены используется команда «Открыть сцену в Godot».

ObjectDefinition прошёл миграции до schema 10: добавлены subcategory, сохраняемые relations, данные спрайта и настройки коллизии. Relations проверяются на постоянные ID, отсутствие самоссылок и положительное количество; отсутствие цели не превращает связь в право владения ресурсом.

**Проверка:** изменения отправлены в отдельную ветку feature/web-object-builder-godot-integration. На этом этапе проведена статическая сверка связей кода и маршрутов IPC. Запуск Godot 4.7.2 и GUI-приёмка именно этой интеграционной версии ещё не подтверждены.

## 20. Визуальный редактор, спрайты, коллизии и связи механик

- Добавлен левый раздел **«Внешний вид»** с загрузкой PNG/JPEG/WebP (лимит 5 МБ, проверка декодирования и разрешения), заменой и удалением изображения. Удаление спрайта не удаляет исходный файл.
- Текстура хранится внутри `ObjectDefinition.preview_texture`; хэш версии позволяет восстановить изображение при синхронизации черновика, отмене изменений и повторном открытии. Пустой спрайт показывает эмодзи-заглушку.
- Для спрайта настраиваются независимый масштаб X/Y, смещение X/Y и Z-index. Эти же параметры применяются к узлу `Sprite2D` в сцене Godot и отображаются в центральном предпросмотре.
- Добавлен левый раздел **«Коллизия»**: включение, твёрдый режим или Area, прямоугольник/круг/капсула, размеры, смещение, слой и маска. Слои показываются с именами из Project Settings, а не только числами.
- При сохранении управляемые визуальные и collision-узлы синхронизируются в `PackedScene`. Узлы помечаются служебной метаинформацией; синхронизация удаляет только узлы, принадлежащие редактору, а пользовательские узлы и коллизии сцены сохраняет.
- Сохранение определения и сцены связано rollback-процедурой: при ошибке записи определения сцена возвращается к предыдущим байтам; для новой сцены удаляется только файл, созданный этой неудачной операцией.
- Связи механик сгруппированы внутри карточек добычи/сбора, производства, рецептов и разрушения. В группах доступны выбор цели, количество, переход к объекту и создание отдельного связанного объекта. Общая вкладка показывает исходящие связи, группировку по владельцу и обратные ссылки.
- Типы `drop`, `harvest`, `produce`, `input` и `remains` требуют соответствующую механику-владельца. Общая связь оставлена только для простого отношения `related`; backend проверяет владельца, тип связи, дубли и самоссылки.
- Связь является ссылкой, а не вложенным объектом: удаление или изменение связи не удаляет целевую запись библиотеки.

**Границы реализации:** параметры спрайта и форма коллизии записываются в сцену Godot. Связи, типы результатов и количество сохраняются в нативной модели; фактический runtime-спавн предметов/результатов по этим связям требует отдельной игровой логики и здесь не заявляется как уже работающий.

**Проверка:** JavaScript прошёл синтаксическую проверку через V8; маршруты IPC, поля сериализации и вызовы нативного сервиса сверены статически. Godot 4.7.2 в этой среде не запускался, поэтому синтаксис GDScript, импорт текстуры, открытие сцены и физические столкновения нужно подтвердить в самом редакторе.


## 21. Левая панель редактора, связанные черновики и редактор спрайтов

### Компоновка интерфейса

- Инструменты **«Части»**, **«Внешний вид»** и **«Коллизия»** находятся в левой панели рядом с центральным предпросмотром. Правая панель оставлена для основных данных, поведения, компонентов и связей.
- Кнопка **«Сохранить»** расположена в панели самого редактора рядом с масштабом/состоянием предпросмотра. Сочетание Ctrl+S вызывает тот же сценарий сохранения.
- В разделе «Части» показывается дерево узлов и параметры выбранной части. Инструменты внешнего вида и коллизии больше не спрятаны среди правых инспекторных вкладок.

### Связи и сохранение комплекта

- Связанная цель может быть как сохранённым объектом, так и открытым черновиком. Создание цели из карточки механики больше не сохраняет её немедленно: новый объект остаётся самостоятельным черновиком.
- Перед сохранением основного объекта редактор обходит исходящие связи и показывает окно комплекта. В нём можно выбрать связанные черновики — как новые объекты, так и открытые изменения уже существующих записей, — которые нужно сохранить в библиотеку вместе с основным объектом. Уже сохранённые и не изменённые цели не предлагаются повторно.
- Связанные ObjectDefinition сохраняются как отдельные ресурсы со своими сценами и постоянными ID. Родитель не поглощает дочерние данные; удаление связи не удаляет её цель. Сохраняемые черновики записываются раньше основного объекта, чтобы родительская ссылка не указывала на ещё не созданную запись.
- Пример для дерева:
  - связь механики разрушения **«Что выпадает» (drop) → «Древесина»** описывает выдачу ресурса, количество и размещение рядом с родителем;
  - связь **«Остаётся после разрушения» (remains) → «Пень»** задаёт замену исходного дерева остатком на месте.
- В связи хранятся настройки placement, local_position, rotation и local_scale. Режимы размещения включают появление/выпадение рядом, замену исходного объекта, прикрепление и расходование. Локальные координаты задаются относительно родителя, а не в мировых координатах.

### Планируемый редактор совмещения объектов

Следующий этап для механик drop, remains, attach и похожих сценариев — **совместный 2D-редактор связанного комплекта**. Его нужно реализовать как отдельный режим предпросмотра связи, не смешивая ресурсы объектов и не превращая ссылки в каскадно удаляемые вложения.

Планируемое поведение:
1. Слева выбирается родительский объект, а справа/в списке — связанный дочерний объект; центральная область показывает их одновременно в одной системе координат.
2. Дочерний объект можно перетаскивать мышью относительно родителя. Положение отображается в локальных X/Y и редактируется также численно.
3. Для дочернего объекта доступны поворот, независимый масштаб X/Y, привязка к сетке, сброс трансформации и визуальная точка привязки (pivot).
4. Переключение связи показывает разные состояния: например, древесина в позиции выпадения и пень, совмещённый с основанием дерева.
5. Трансформация сохраняется в настройках конкретной связи (local_position, rotation, local_scale, будущие pivot и z_index). Один целевой объект может иметь разные трансформации у разных родителей.
6. Изменение дочерней записи в библиотеке не должно незаметно менять локальную трансформацию других связей; сами целевые объекты остаются независимыми ObjectDefinition.

Это **план**, а не уже готовая возможность: текущая версия сохраняет локальные параметры связи и показывает их в карточке, но интерактивного перетаскивания связанных объектов в общей сцене пока нет.

### Размеры и spritesheet

- ObjectDefinition обновлён до schema 10. object_size хранит логический габарит объекта в мире отдельно от исходного размера изображения и масштаба спрайта.
- Размер объекта задаётся шириной и высотой. Он отображается в центральном предпросмотре как отдельная рамка и сохраняется в метаданных корневой сцены. Размер коллизии по-прежнему настраивается отдельно.
- Для статического спрайта можно задавать отображаемую ширину/высоту, масштаб X/Y, смещение и Z-index. Отображаемый размер вычисляется из текстуры и масштаба; изменение габаритов объекта не меняет текстуру.
- Встроенный редактор spritesheet имеет пиксельные линейки сверху и слева, масштаб просмотра, сетку строк/столбцов и выделение диапазона кадров.
- Каждая анимация хранит имя, число строк и столбцов, индекс строки, стартовый столбец, количество кадров, внешние отступы X/Y, промежутки между кадрами X/Y, FPS и loop. Можно выбирать диапазон кадров непосредственно мышью на листе; несколько анимаций могут использовать разные строки одного spritesheet.
- При синхронизации сцены ObjectBuilderSceneDraftService формирует SpriteFrames с AtlasTexture и управляемый AnimatedSprite2D. Если анимации не заданы, остаётся обычный Sprite2D.

### Технические границы

- Параметры связи являются декларативными данными. Реальное выполнение механики — выдача древесины при рубке и замена дерева пнём в работающем игровом мире — потребует следующего этапа runtime-интеграции. Редактор сейчас не должен сообщать пользователю, что эти игровые события уже исполняются.
- object_size является отдельным логическим габаритом/рамкой редактора. Это не автоматическая замена размера CollisionShape2D: физическая форма, режим, слой и маска по-прежнему задаются независимо.
- Интерактивное совмещение нескольких связанных объектов указано в плане выше; локальные координаты связи уже хранятся, но общий manipulation viewport ещё не реализован.

**Проверка:** JavaScript синтаксически проверяется через V8; после этих изменений необходимо выполнить импорт spritesheet, сохранить несколько анимаций, повторно открыть объект и проверить построение AnimatedSprite2D в Godot 4.7.2. В текущей среде запуск Godot и GUI-приёмка не подтверждены.

- Нижний блок «Поведение · Подключённые механики» в левой панели теперь сворачиваемый и по умолчанию закрыт. Количество подключённых механик остаётся видимым в заголовке; список действий раскрывается только по запросу.

  - дуб, сосна и пальма связаны с древесиной и пнём, который заменяет дерево на его месте; сухое дерево и пень дают древесину;
  - фруктовое дерево, ягодный куст, трава, гриб и фермерские культуры связаны с результатами сбора;
  - курица, корова, овца и свинья связаны с яйцом, молоком, шерстью и трюфелем;
  - печь, верстак и наковальня содержат пример входных материалов и результата изготовления.

- Целевые встроенные шаблоны теперь разрешаются в списке связей и отображаются как полноценные цели. Идентификаторы остаются самостоятельными ObjectDefinition; ссылки не превращаются во владение и не включают каскадное удаление.
- Предустановленную связь можно отредактировать даже тогда, когда её механика пока не подключается в этом проекте. Это не включает запланированную механику и не делает её исполняемой: добавление новых связей по-прежнему требует доступной подключённой механики.
- Граница реализации: связи хранятся как конфигурация ObjectDefinition. Выдача ресурсов, замена дерева пнём, сбор урожая, производство животных и рецепты в игровом рантайме не начинают исполняться только от добавления этих данных; для этого требуется отдельная runtime-интеграция.

Проверка: JavaScript проходит синтаксическую проверку через V8. Для встроенных связей выполнена статическая проверка целевых ID, типов связей и владельцев-механик; запуск Godot 4.7.2 и GUI-приёмка в этой среде не подтверждены.



## 23. Объекты в файловой системе, нативная панель и размещение в мире

### Единая структура файлов

Сохранённая запись и её сцена используют одно название, категорию и постоянный ID:

```text
res://data/object_library/
  objects/
    Природа/
      Дуб.tres
      Камень.tres
    Ресурсы/
      Древесина.tres
  templates/
    Природа/
      Дуб.tres
  scenes/
    objects/
      Природа/
        Дуб.tscn
        Камень.tscn
      Ресурсы/
        Древесина.tscn
    templates/
      Природа/
        Дуб.tscn
```

- Категория становится папкой, а `display_name` — именем файла и корневого узла сцены. Имена с пробелами и кириллицей сохраняются; недопустимые для файловой системы символы безопасно очищаются.
- ID объекта не зависит от пути. Переименование или перенос в другую категорию меняет путь ресурса/сцены, но не ID и не ссылки на объект.
- Если среди уже сохранённых объектов той же коллекции есть такое название, при фактическом сохранении добавляется `(2)`, `(3)` и т.д. Проверка имён глобальна в пределах объектов или шаблонов, даже если категории различаются. Простое создание копии из шаблона само по себе не добавляет слово «копия».
- Старые ID-имена файлов остаются читаемыми. При следующем сохранении объект переводится на структуру по категории и названию. Старый файл удаляется только после успешной записи нового.

### Нативная панель Godot

Добавлена отдельная панель **«Объекты»** в левый док Godot, не встроенная веб-страница. Она работает непосредственно с `ObjectDefinition` из нативной библиотеки.

- Группировка по категориям, фильтр категории и поиск по названию/категории/тегам.
- Двойной щелчок по строке или кнопка **«Открыть в Object Builder»** ведёт на страницу соответствующего объекта.
- **«Показать сцену в файловой системе»** выбирает связанный `.tscn` в FileSystem dock. Если сцена ещё не синхронизирована со свежим определением, она создаётся/обновляется перед выбором.
- Список обновляется при изменении файлов проекта и после сохранения через нативный редактор.

### Перетаскивание в игровой мир

Объект в библиотеке является повторно используемым prefab-сценой. При перетаскивании строки из панели в 2D-окно Godot панель отдаёт стандартный file-drag payload с путём его `.tscn`. 2D-редактор Godot принимает сцену как новый экземпляр в текущей открытой сцене. Это использует обычный механизм перетаскивания файлов/сцен в редактор, а не отдельный HTML-canvas.

- Если сцена отсутствует или осталась по старому пути, она подготавливается из актуального `ObjectDefinition` перед началом drag.
- Библиотечный ресурс не перемещается и не переименовывается от размещения. В мир добавляется отдельный экземпляр PackedScene; можно перетаскивать несколько экземпляров одного объекта.
- Положение экземпляра выбирается стандартным 2D-редактором при отпускании. Привязка к сетке и дальнейшее перемещение/поворот/масштабирование остаются инструментами редактора сцены, а не изменениями исходного объекта в библиотеке.
- Изменение исходного объекта выполняется через его страницу Object Builder; это не должно незаметно менять ID или путь уже размещённых экземпляров.

### Постоянная ссылка Object Builder внутри объекта

Каждая генерируемая сцена получает дочерний узел `ObjectBuilderReference` с экспортируемыми полями:

- `object_id` — постоянный ID определения;
- `builder_uri` — ссылка вида `objectbuilder://object/<ID>`;
- `display_name` и `category`;
- `definition_path` — текущий путь к `.tres`.

Это служебная ссылка, а не родительский игровой компонент. Её экспортируемые свойства сохраняются вместе с PackedScene; служебный узел не отвечает за runtime-поведение объекта. Для сцен, созданных до появления этого узла, Inspector дополнительно пытается найти определение по пути открытой сцены. Сам док сделан через `EditorDock` Godot 4.7; API помечен в документации Godot как экспериментальный и может измениться в следующих версиях. В Inspector зарегистрирован `EditorInspectorPlugin`: при выборе корневого объекта или самой ссылки он показывает кнопку **«Открыть страницу»** и URI. Кнопка переключает на вкладку Web Object Builder и открывает нужный объект по ID. Тот же блок доступен при выборе самого `ObjectDefinition` в Inspector.

### Границы и проверка

- Перетаскивание добавляет экземпляр сцены в текущую сцену Godot; оно не создаёт игровой spawn-point, не выполняет механику drop/remains и не настраивает точки появления игровых ресурсов.
- Нативная панель показывает сохранённые объекты библиотеки, не несохранённые черновики вкладок. Сначала нужно сохранить объект, затем он появляется в панели.
- Встроенные/пользовательские шаблоны остаются источником создания объектов и не перечисляются как готовые экземпляры в панели размещения.
- Структура и маршруты проверены статически; JavaScript прошёл синтаксическую проверку, пути файлов согласованы с сервисом библиотеки, а script-ссылки подключены к генерации сцен и Inspector. Запуск Godot 4.7.2, проверка GDScript компилятором и реальный drag/drop в 2D-viewport в этой среде не выполнялись.
